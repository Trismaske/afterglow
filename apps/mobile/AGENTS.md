## State model (the thing to understand first)

**Read [docs/STATE_MODEL.md](../../docs/STATE_MODEL.md) FIRST.** m0.8.2 (schema v19) split what a photo carries into three layers, and every surface below implements them: exactly one VERDICT in `photos.state` (`unreviewed` / `kept` / `culled` / `trashed` — `to_edit` is gone, `done` is spelled `kept`), any number of independent pending ACTIONS in `photo_actions` (one shape for edit · favourite · organize · share, replacing three column groups plus the old `share_queue` table; `db/actions.ts`), and ANNOTATIONS that are never states (in a group, time-attached, best). The edit queue holds any LIVE photo with a queued edit, decided or not — flagging an undecided photo ("the edit is what tells me whether to keep it") is legitimate, and completing that edit leaves the verdict alone. Queue membership is `state IN ('queued','error')` AND the photo is still live work — a staged cull or trashed photo leaves every queue (`livePhotoClause`), while its action rows survive so un-staging restores them. `resolved_at` is PERMANENT: clearing a queue is not forgetting, which is what makes base rates and turnaround stats possible — and every exit from a queue goes through `leaveQueue`, which ALWAYS runs two statements (drop the row that never completed, demote the one that did); writing only the delete strands a re-queued-after-applying row at `state='queued'` forever. A successful share pass stamps `resolved_at` on its members while leaving them queued, because multi-pass sharing is the feature and the batch event is share's only completion signal.

**SQLite is the ONLY review state (m0.8 — sessions are gone).** The continuous scan (`scan/scanRunner.ts`) pages MediaStore newest→oldest on app open, embeds + hashes each merge window natively (`lib/embeddings.ts` → `modules/image-embedder`), groups it with core `groupByEmbedding`, and lands groups in the durable tables (`db/store.ts writeContinuousGroups`, honoring the regroup boundary: reviewed groups and user-ejected singles are never rewritten — `lib/regroupBoundary.ts`, re-checked inside the write transaction). `review/ReviewContext.tsx` reads the queue (`listReviewGroups`/`listSinglesFeed` — the pending feed keeps staged culls badged — and derives the merged `timeline` from the two pages via `lib/timeline.ts`; `loadGroup` fetches a completed group for browse/re-decide, `loadDeckSingles` a day's or run's rows through the WIDER deck predicate that keeps kept singles in place badged; `releaseBrowseIds` drops those browsed ids when Home refocuses) and writes decisions directly (`applyReviewDecisions`; a write resolves at COMMIT, applies the parity-tested optimistic patch `lib/reviewPatch.ts`, and reconciles via a background refresh — m0.8.1 responsiveness; `queuedFor`/`refreshQueuedFor` carry share/organize queue membership for the badges, re-read rather than patched; `actionWeights` adds the m0.8.2 CARRIED half — live comes from the patched refs so a chip lights on tap, carried only from the last read, because nothing is carried until the work completed): keep writes `kept` at swipe, cull stages the durable global cull queue, the Edit chip queues an edit ACTION without touching the verdict, and an active-verdict tap clears to `unreviewed` — which likewise leaves actions alone, because the layers are independent. `reviewed_at` first-stamps on any verdict; `decided_at` re-stamps on every one. Un-staging a cull lands on `kept` and its queued edit rides along (CullList "Restore" lands on `unreviewed`). NO verdict path touches an action: even the re-decide sheet's explicit "Keep" leaves a queued edit alone, because only the edit's own control retires an edit. Startup recovery (interrupted trash/share batches) runs once per process in the provider. m0.7 hardening that survives unchanged: trash-attempt lifecycle (`db/trashStore.ts` + `lib/trashFlow.ts`: prepare/reserve → launching → tri-state verify, at-most-once credit), edit-lifecycle coherence (the cycle key is now the edit action's `queued_at`; copy-match resolution; a detected edited COPY is recorded as kept with NO edit action of its own — it is the result of the original's edit, and the relationship lives in `edit_copy_matches`), share (`db/shareStore.ts`) and organize (`db/organizeStore.ts`) durable queues. Both removal affordances use the local Android 11+ `modules/media-store-actions` trash request; never add a permanent-delete fallback. Settings are key/value rows parsed with fallback-to-default (pattern: `comparePrefs.ts` / `accentTheme.ts`).

**m0.8.1 scan skip:** a pass whose `scanSkip` fingerprint matches the last COMPLETE clean pass returns immediately — MediaStore's per-volume generation is OS proof nothing changed, so an unchanged library costs one native call instead of a full re-walk. `requestRescan` (settings applies/resets) forces a pass.

`scan/scanRunner.ts` is the m0.8 continuous-scan
orchestrator (single-flight per process, Home starts it once permission
lands): merged newest→oldest paging → merge windows → embed (cache-aware) →
core `groupByEmbedding` → regroup boundary → `writeContinuousGroups` into the
one 'continuous' grouping run; exports the observable `ScanStatus` (gate-4
Home surface — m0.8.2 F3/F4: `total` is a FULL pass's denominator (Home +
Settings render the percent from it; a delta keeps it null and shows plain
counts) and `corpusTotal` is the pass-start library snapshot Home's
"N pictures total" line reads while scanning, so the card and the scan line
can never quote two different library sizes; the scan line dropped "groups
found" — the card carries the one truthful group count). **m0.8.2 DELTA SCAN:** `planPass` asks MediaStore what changed
since the stored per-volume generation and decides delta-vs-full by the
photo-equivalent cost model; `pageAndGroup` then runs EITHER kind — a full
pass is a delta pass over one unbounded range — so the two cannot drift
apart. Deletions arrive as trashed rows (Android 11+ gallery deletes set
`IS_TRASHED` and keep the row) and are reconciled directly, because the
scan's paging filters trashed rows out. Every uncertainty (no baseline,
model swap, new volume, unplaceable undated change, unreadable change set,
cost model against it) falls back to a full pass. Counts are checked in BOTH
directions: before the pass, `MediaStore < tracked` means something vanished
with no trace (a permanent delete) → full pass; after a delta, the two must
AGREE, and a shortfall means a silently missed addition → full pass
immediately, in the same invocation. A weekly reconciliation outranks the
unchanged-library skip as insurance while the delta is young (docs/TODO.md, "Revisit the weekly full pass"). `db/embeddingStore.ts` owns photo_embeddings (BLOB float32
vectors keyed by asset id + mod_time) and the model-SHA pin whose mismatch
triggers the destructive re-embed event. `modules/media-store-actions` is the
Android 11+ native trash/favourite boundary plus the gate-0 editor-launch
diagnostics (environment/permission probes, intent dispatch probes,
`createWriteRequest`); `modules/material-you-accent` reads the system tone;
`modules/image-embedder` is the MediaPipe MobileNetV3-large embedder
(`embed(uri, decodeCap)`, pinned `MODEL_SHA256`).
