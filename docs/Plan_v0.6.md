# Plan v0.6 — The RAW pipeline + Lightroom companion plugin

*The release plan for desktop v0.6, answering `docs/Feedback_v0.6.md`.
Evidence and decision history: `docs/Investigation_v0.6.md` (delete both once v0.6 ships and PLAN.md absorbs what remains).
Version 0.5.0 → 0.6.0, tag `desktop-v0.6.0` (`scripts/release-preflight.mjs` requires the full-semver desktop tag `desktop-v${version}`), branch `initial`.
Ridealong: the already-committed windowed-settings/app-icon and desktop-hardening work since `desktop-v0.5`.*

## What ships

RAW files enter the slideshow, rendered with the user's edits by the editor that owns them:

1. **darktable edits** (`X.ext.xmp`, `darktable:` namespace) → `darktable-cli` render. Faithful.
2. **RawTherapee edits** (`X.ext.pp3`) → `rawtherapee-cli` render. Faithful.
3. **Lightroom edits** (`X.xmp`, `crs:` namespace, incl. AI masks) → the **Afterglow companion plugin** running inside the machine's own LR Classic, always against a **dedicated Afterglow render catalog** (import → forced sidecar read → `LrExportSession`); user catalogs are never imported into or metadata-read. Faithful — AI-mask photos included: mask corrections render from RAW + XMP alone, dialog-free, with both LR prompts suppressed via verified preference keys (spike-verified 2026-07-29). Requires LR installed + running (Afterglow manages LR's lifecycle; jobs defer while a user's own LR session is open).
4. **No edits, no editor, or no reproducible route** → an existing JPEG or the embedded camera preview, always labeled, per the settings below.

### The rendering predicate

One rule decides both what the show displays and what the organizer inherits:

> **Render the RAW unless the RAW cannot reproduce what an existing JPEG already contains.**

A JPEG sibling is therefore **never a convenience display source** — it displays only when it is the more faithful artifact. When an editor's sidecar exists and is renderable, the render is faithful and the JPEG is provably redundant inventory. When **no sidecar exists**, a render could only be a default demosaic, so the JPEG — carrying either lost edits or the camera's own processing — always displays, whatever the classifier says: **display never depends on the classification heuristic**; the classifier routes only the inventory category. "Reproducible" means **no edit information exists only in the JPEG** (camera processing is not edit information, so an in-camera JPEG remains a deletion candidate); it never claims pixel equality.

Applied per photo:

| Files present | Displayed | JPEG's inventory category |
|---|---|---|
| RAW + one editor's sidecars, renderable | JIT render | `redundant-export` |
| RAW + sidecars from 2+ editors | JIT render of the **newest sidecar's** editor, badged | none — not provably reproducible until resolved; the **RAW** carries `multi-editor-conflict` |
| RAW + JPEG, no sidecar | the JPEG, labeled | by classifier verdict: **in-camera** → `redundant-export`; **export** / **ambiguous** → `export-only-edits` — **never a deletion candidate** |
| RAW alone (no sidecar, no JPEG) | embedded preview, or a render when the preview would be upscaled | n/a |
| JPEG with no RAW | the JPEG | n/a — untouched, unflagged (the 1991–2010 era of the family library is this) |

Rendering is **just-in-time and ephemeral**, never a persistent cache. The show maintains a moment-aware **look-ahead queue** (**depth is a setting, default 10 slides** — renders start this many slides ahead so →-navigation is ready too; when the mix engine picks a moment, all its members queue at once so they land as the moment plays, even beyond the depth). Artifacts are deleted once their item leaves the recent-history window (so ←-navigation stays instant) and re-rendered on the item's next appearance; compute is deliberately spent freely, the machine is idle while the screensaver runs.

### Sibling classification

Telling a lost-sidecar export from an in-camera RAW+JPEG pair is the only judgment in the table, and it decides whether v0.7 may ever propose deleting the file. Signals, all from a single batched exiftool pass over sibling JPEGs: `Software` / `XMP-xmp:CreatorTool` (an editor export stamps its product name; an in-camera JPEG stamps camera firmware), MakerNotes completeness, the JPEG's write time against the RAW's `DateTimeOriginal`, pixel dimensions against the RAW's full resolution, and location (a `JPEG\` subfolder is an export convention, a same-folder sibling is not evidence either way).

The classifier is pure and returns `'in-camera' | 'export' | 'ambiguous'`; its verdict is recorded in the flag entry and badged on screen, so a wrong call is visible and correctable in v0.7 — and since display never depends on it, a misclassification can mislabel an inventory row but never change what plays. `ambiguous` files as `export-only-edits` (protected): misfiling a deletion candidate as protected costs a stale inventory row, while the reverse destroys the only copy of someone's edits. P3 logs the ambiguous rate so the heuristic's real-world hit rate is measured, not assumed.

**exiftool must run in batch mode** (`-stay_open`, or an `-@` argfile) with results cached in the index against each JPEG's mtime/size. One process per file at ~0.1 s would make a first scan of the family library's sibling set take tens of minutes; batched it is single-digit milliseconds per file, and incremental afterwards.

### The export inventory

Every JPEG sibling of a RAW is flagged **at scan time**, not on appearance, so the queue is a complete work list for v0.7 rather than a record of what happened to play. This costs nothing extra: RAW+JPEG pair de-dup (a RAW and its sibling are one photo in the draw) already requires sibling pairing during indexing.

Flag entries carry **automatic provenance** and one of the categories above, plus a **cheap staleness hint** — the sibling's mtime against the newest edit sidecar's mtime — so v0.7 can sort outdated exports first. No content digests, no persisted digest history, and no freshness contract: since a sibling is never trusted for display, nothing rests on proving it current. (Sidecar content digests still exist, but only inside the render-identity key, where a mtime-preserving sync rewrite must invalidate a buffered render.)

`multi-editor-conflict` flags target the **RAW**; every other automatic category targets the **JPEG's own path**, because the export is the review subject. Automatic flags are removed when the underlying file disappears and are otherwise durable; a user dismissal is durable and never re-raised, because the condition it describes cannot silently reverse. Dismissals are their own records keyed by path + category — never the mere absence of an entry, which a rebuild would resurrect.

The inventory is governed by one setting, **Track JPEG exports for cleanup (default on)**, covering both export categories; `multi-editor-conflict` always flags — it is a display-correctness signal, not inventory. Off means off: creation stops and existing automatic export entries (with the "flagged" aspect of their markers) are deleted. Turning it back on rebuilds the complete inventory **immediately from the persisted index** — pairs, classifications, and staleness hints live in the index, so the rebuild is one batch insert with no filesystem walk, no exiftool re-runs, and no waiting for a scan. Dismissal tombstones and manual flags survive the toggle in both directions.

### On-screen honesty

A **small persistent marker** sits in a screen corner for the whole slide whenever the displayed artifact is not the plain case — an export or camera preview is being shown, or editors disagree. The marker is **display honesty, independent of the tracking switch**: nothing is ever substituted silently. The full wording — which file, which category, whether it is flagged — lives in the on-demand `O` info overlay (the "flagged" aspect appears only while tracking is on). The marker is quiet enough not to fight the photo, which matters because in the family library's 2026 folder it applies to nearly every slide. In state-model terms the marker is an **annotation** (a fact about what is displayed, never a decision), so per `docs/STATE_MODEL.md`'s visual rules it renders neutral — never a verdict or action hue.

One setting governs the chrome: **On-screen status markers (default on)** silences the routine kinds — the corner markers and the render-wait status — for viewers who want clean photos and have consciously traded ambient awareness for them (the honesty stays available in the `O` overlay). Operational statuses (the low-disk pause) and actionable failure messages ("nothing can display with current settings") are never suppressible. The rule: **everything routine is silenceable; everything actionable is not.**

Also in scope: FUSE/network-mount exclusion (new folder selection **and** persisted folders validated at startup before any traversal), and the feedback fix — the flag queue reachable from the settings screen.

Explicitly **not** in v0.6: acting on flags (v0.7 organizer), refreshing the user's own exported JPEGs in place, HEIC, Lightroom preview-cache extraction (rejected — see PLAN.md).

## Verified constraints the implementation must honor

- **darktable-cli**: private `--configdir` per install (default configdir deadlocks under flatpak PID namespace; stale `.lock` files after crashes must be cleaned); renders serialized (concurrency 1 — parallel configdirs contend badly: 6.2 s solo against 19.8 s parallel); **output path must use forward slashes on Windows** (darktable's filename-template engine eats backslashes); `--library :memory:`; sidecar passed explicitly.
- **rawtherapee-cli**: `-S` renders only-if-sidecar (explicit error otherwise — clean detection); Windows install dir is versioned (`RawTherapee\5.12\`) — discovery globs it; Linux discovery covers native + flatpak (`org.darktable.Darktable` / `com.rawtherapee.RawTherapee` with `--filesystem` for paths outside host scope).
- **Render time is unbounded by design.** Measured on the deployment machine (i5-11400): darktable/RT 3–8 s per photo; the LR plugin round-trip (import → `readMetadata` → export) 5–6.5 s warm single photo, ~4.9 s/photo batched, ~10 s for the first photo after launch, and LR itself takes ~12 s from process start to the watcher being operational (all measured 2026-07-29). But the machine is whatever the family owns, and a slow machine must never produce an error, a penalty, or a mystery. The rules: renders are serial and never on the display path; the look-ahead **substitutes** the next ready item first (a passed-over item is deferred, not discarded, and re-slots when its render completes); only when *nothing* is ready does the current slide hold. A holding slide surfaces a quiet status once it has overrun its configured interval by **max(3 s, 25 % of the interval)** — the grace period scales with the user's own interval so a 30-second setting does not nag after three — reading as *"Rendering next photo…"*, never as a fault. **Quality is never traded for speed**: no adaptive downscaling, no timeout that abandons a render.
  Two consequences to state plainly in the settings copy, because they are inherent rather than fixable: look-ahead depth absorbs **bursts, not a sustained deficit**, so on a machine slower than its slide interval the show is paced by the renderer whatever the depth; and settings shows the **measured median render time per editor** so a slow machine is legible where it can be acted on, rather than nagged about over the photos.
- **Lightroom plugin**: import alone loads no sidecar edits — `photo:readMetadata()` is required and works, and **both LR prompts are solved** (suppressed durably via preference keys: `doNotShowPrompts`/`AgLibrary_readMetadata` for the metadata-read prompt, `AIUpdateWarning_shouldUpdateAffectedPhotos = true` for the AI-updates dialog — the latter spike-verified 2026-07-29 on a **fresh** import of an AI-mask photo, the previously unproven case). AI-mask edits render faithfully from RAW + XMP alone: stripping the mask block changes the output (RMSE 2.1 %) while removing the `.acr` changes nothing — the `.acr` contributes zero rendered pixels, so no photo is unrenderable for mask reasons. LR GUI must be running. **Catalog isolation is absolute**: Afterglow launches LR minimized with its own render catalog and closes only instances it launched — gracefully first; an Afterglow-owned instance that ignores the graceful path may be force-closed after a generous grace period (the render catalog is disposable by design), while a **user's session is never force-killed** (a blocked user-session close is logged and left alone). A user's own LR session (any other catalog) is never reused — imports and forced metadata reads there could pollute the catalog or overwrite newer unsaved edits — so LR jobs defer, surfaced honestly, until the user's session closes. **One opt-in exception to the close policy** (`close-Lightroom-on-screensaver-start`, default off): only on a **screensaver-triggered launch** — which requires a **distinct provenance signal in launch parsing**: today `parseLaunchMode` collapses win32 `/s` and manual `--show` into one mode, so `LaunchInfo` gains a `screensaver` flag set only by OS idle triggers (`/s`; never the Start button or `--show`, since the user may be active), **and that provenance must survive the single-instance handoff**: `/s` arriving while an instance is already open loses the lock and reaches the existing process via `second-instance`, which today ignores non-settings launches — the forwarded argv must start the show with screensaver provenance intact (gated) — a user-owned session may be closed gracefully — a blocked close falls back to deferral, force-kill never happens — after which Afterglow launches its own render-catalog instance.
- **Detection rules**: `X.ext.xmp` + `darktable:history_end>0` → darktable; `X.ext.pp3` → RT; `X.xmp` + `crs:HasSettings` → LR; else embedded edit-namespace XMP; else no edits. Multiple *files* from one editor are normal and not a conflict (an LR asset legitimately carries `X.xmp` **and** `X.acr`). When a RAW carries valid sidecars from **more than one editor** (plausible mid-migration, e.g. an RT-era `.pp3` beside a newer darktable `.xmp`), the **newest sidecar wins** — last-edited editor owns the current look, never a fixed type priority — the show renders that editor's result and **badges the slide**, and the RAW is **flagged `multi-editor-conflict` for human review**. Both sidecars stay untouched, so a wrong pick is fully recoverable, and the JPEG sibling is withheld from the inventory because it may have been exported through the losing editor. Ordering uses sidecar mtimes; when genuinely unordered (equal mtimes) the photo is **not rendered by a guessed editor** — its export or preview shows, labeled, until the user edits again or resolves the flag. **Embedded edit namespaces participate in the same selection**: a DNG carrying embedded `crs:` plus an external sidecar compares the container's mtime against sidecar mtimes under the same newest-wins rule. darktable sidecars with `xmp:Rating="-1"` (rejected) are excluded from rotation. crs XMPs are **never** fed to darktable-cli (verified silently ignored).
- **Embedded preview adequacy**: a preview is adequate when displaying it involves no upscale — `s = min(screenW/previewW, screenH/previewH)`, adequate when `s <= 1`, computed against the show window's size. Aspect-fit is the correct comparison, not area or per-dimension: CR3's 1620×1080 preview is exactly adequate on a 1080p screen (it letterboxes to 1620×1080) and upscales 1.33× on 1440p. Verified preview sizes: NEF `JpgFromRaw` full-res (4288×2848), CR2 full-res, CR3 1620×1080 only, ARW `PreviewImage` 1616×1080 (newer bodies add full-size `JpgFromRaw` — try first), DJI DNG 960×544. Extraction is ~0.1 s, roughly 40× cheaper than rendering.
- **Flag model must change in core.** `FlagEntry` is `{path, flagType, at, note?}` with `flagType` locked to the six user intents ([packages/core/src/flags.ts:12](../packages/core/src/flags.ts#L12)), so automatic categories cannot ride on `flagType` without collapsing into `review` and losing exactly the distinction the organizer needs. Required: a `source: 'manual' | 'automatic'` field, an automatic `reason` (the categories above), the classification verdict and staleness hint, a dedupe key extended past `(path, flagType)` so a manual `delete` and an automatic `redundant-export` on one path cannot collide ([flags.ts:45](../packages/core/src/flags.ts#L45)), and a **batch `addFlags`** with a Set-based index — bulk-flagging thousands of siblings through the existing per-add linear scan plus one atomic whole-file rewrite each is quadratic and unusable at scan scale. JSON goes to `version: 2`, and the v2 reader accepts v1 by stamping existing entries `manual` so the soak tester keeps the flags they captured (a one-way migration, deletable at v1.0). **Cross-app alignment (deliberate — `docs/STATE_MODEL.md` is the contract)**: desktop flags map onto mobile's shipped three-layer model rather than inventing a parallel one. Manual E/M/N/T flags are **actions** (mobile's exact shape: kind, `queued | applied | error`, target — v0.7 adopts it when flags become workable); a D flag is intent toward the **verdict** path (`culled → trashed`, staged then executed, out of `PHOTO_STATES` as shipped: unreviewed/kept/culled/trashed); and every automatic entry is an **annotation** — a scan fact, never a decision, exactly the layer STATE_MODEL.md defines. A flag entry itself is queue membership + provenance and never carries a review state, mirroring mobile's queues-vs-photos separation, so v0.7 attaches verdicts to reviewed files without remodeling the queue and a desktop review reads exactly like a mobile one.
- **Formats**: NEF/CR2/CR3/ARW/DNG are first-class — each render-verified through the pipeline before release (NEF/ARW already verified; **CR2/CR3/DNG live-render verification is part of P2's gate**; CR3 is the family's current-camera format — non-negotiable). Other RAW extensions are accepted but documented untested.

## Phases

Each phase lands with its tests and doc updates; gates are demo-able.

**P1 — Detection core (pure).**
`main/raw/detect.ts`: scan-result classifier → `{ editor: 'darktable'|'rawtherapee'|'lightroom'|null, sidecarPaths, embedded: { containerMtime, containerSize } | null, conflict: { editors, chosen, reason } | null, rejected }` from sidecar presence + namespace sniff + embedded-XMP scan. `sidecarPaths` lists **every** edit dependency from the owning editor; `conflict` carries the multi-editor diagnostic that drives the badge and the flag.
Alongside it, `main/raw/siblings.ts`: the pure sibling classifier — supplied exiftool fields and pair geometry in, `'in-camera' | 'export' | 'ambiguous'` plus the resulting inventory category out. Both modules are pure; the impure exiftool batch and directory pairing live in P2/P3 bindings.
Embedded XMP + preview extraction + sibling metadata need a tool on all platforms: bundle per-platform `exiftool` standalone binaries (industry standard; also fixes the deployment machine, which has none) rather than hand-writing TIFF/CR3 parsers. Checkpoint before the binaries land: confirm per-platform payload size (~10–15 MB expected) and redistribution licensing (Perl Artistic / GPL dual).
Gate: unit tests over fixture sidecars (real darktable/RT/LR samples, DJI factory-XMP negative case); **the multi-editor contract** — ordered conflicts in both directions selecting the newest editor and emitting the diagnostic, an `X.xmp`+`.acr` pair proving multiple files from one editor is *not* a conflict, genuinely unordered conflicts refusing to guess, and embedded-vs-sidecar recency participating in newest-wins (a fixed-priority resolver must fail this gate); **the sibling classifier** — a real Lightroom export, a real in-camera RAW+JPEG pair, a `JPEG\`-subfolder export, and a deliberately signal-poor case landing on `ambiguous` and therefore protected; and **preview adequacy** — the aspect-fit rule asserted at its boundaries with CR3-on-1080p adequate and CR3-on-1440p not.

**P2 — Renderers + look-ahead scheduler (main).**
`main/raw/renderers.ts`: `execFile` wrappers (darktable, RT, exiftool preview) with per-editor discovery (PATH, flatpak IDs, Windows registry/default dirs incl. versioned RT) surfaced in settings, plus the batched exiftool session used for sibling metadata and preview extraction.
The **look-ahead scheduler** watches the playlist's upcoming window (moment-aware: a chosen moment queues all members immediately), resolves each item through the rendering predicate, and renders serially into the **ephemeral buffer**: entries keyed by full render identity `(path, RAW mtime+size, every edit-sidecar content digest, artifact route + renderer/plugin version, output-affecting settings, output size)` so a wrong-route or outdated artifact can never answer. **Buffer lifecycle**: entries are deleted when their item leaves the recent-history window (←-navigation stays instant); during-show usage is bounded by **(history size + look-ahead depth + largest queued moment) × render size**; **abandoned work is disposed too** — when a look-ahead item is invalidated (playlist hot-swap, moment skip) its pending job cancels, a late-arriving artifact is deleted on arrival, and an **already-completed prefetched artifact is deleted immediately** unless still referenced — with a small library the endless playlist repeats identities inside look-ahead + history, so jobs coalesce per render identity and an artifact is deleted only when **no** history or look-ahead occurrence references it; the whole buffer is wiped when the show ends; and a startup sweep removes crash orphans. **External writers are epoch-scoped**: each run stamps a run epoch and the LR plugin writes artifacts only into that epoch's directory, so an export completing after teardown or a crash lands in a dead epoch — sweeps delete every non-current epoch, and the shutdown/adoption handshake quiesces or re-homes in-flight LR jobs before the final sweep (teardown-during-export and crash-restart-during-export are gated) — no LRU, no size-cap setting, no "clear cache" UI, and no path by which the buffer can quietly become a persistent cache.
**Waiting behavior** is the scheduler's contract, not the renderer's: substitute the next ready item, defer the passed-over one, hold only when nothing is ready, and surface the status after the interval-relative grace period. There is no render timeout. The scheduler also records per-editor render durations for the settings readout.
**Disk-space floor**: before each render the scheduler checks free space on the buffer volume (~2 GB floor); below it, rendering pauses — the show continues on exports/previews/skip per settings with an honest "RAW rendering paused: low disk space" status (loud once, never per-photo), auto-resuming when space recovers; a mid-write `ENOSPC` counts as a failed render for that item (falls through to the next display option).
**Documented limitation**: a RAW rewritten with both mtime and size preserved is **undetectable** — no persisted signal changes, and no rescan or index rebuild can distinguish it (there is deliberately no RAW-content digest); classification and renders keep reflecting the old content until the file's observable metadata changes. Accepted: real editors update mtime on save.
Renderers hide behind an interface so tests use fakes; live renders verified by a manual smoke script run on lenny + home-pc, **covering every first-class format not yet verified: CR2, CR3, and DNG** (NEF/ARW are already verified).
Gate: a simulated show with an arbitrarily slow fake renderer substitutes first, then holds with the status appearing at the interval-relative threshold and never an error, with the substituted item re-slotting when ready and disposed only when dropped; the status is proven *absent* on a fast renderer and on a slide that resolves before the threshold; a repeated-item test (library smaller than look-ahead) proves coalesced jobs and no premature artifact deletion; moment pre-queueing proven (all members requested the moment the moment is chosen); buffer identity unit-tested with **an isolated case per key discriminator, each varied alone**: path (two RAWs never share an artifact), RAW mtime only, RAW size only, sidecar digest-only rewrite (mtime and size preserved), artifact route (a preview never answers for an editor render), renderer/plugin version bump, output-setting change, and output size; and the buffer lifecycle verified: deletion on history-exit, cancellation + late-artifact disposal + immediate deletion of already-completed prefetched artifacts for invalidated look-ahead items (hot-swap and moment-skip cases), wipe on show teardown, startup orphan sweep, and the disk-floor pause/resume path.

**P3 — Slideshow integration.**
Scanner accepts RAW extensions and builds the sibling pairing (same basename, same folder **or** the `JPEG\` subfolder one level down) that both pair de-dup and the export inventory consume; the batched exiftool pass classifies siblings incrementally, cached in the index. `afterglow://` continues to serve browser-decodable source media (JPEG/PNG/WebP + videos, per the existing containment) and additionally the contained render-buffer/preview roots — **RAW originals are the only thing never served**.
**Source identity and display URL become distinct playlist fields**: a RAW slide displays its render-buffer/preview URL, but overlay info, manual flags, and queue entries always target the original RAW path (today the renderer passes the display URL to `getItemInfo`/`addFlag`, which would reject or mis-record buffer paths). Automatic export flags target the sibling JPEG's path, per the inventory rules above.
Core flag-model work lands here: `source`/`reason`/classification fields, extended dedupe, batch `addFlags`, and the v1→v2 migration.
New settings in this phase, grouped under a **RAW rendering** section: **unedited-RAW rendering** (render when the embedded preview would be upscaled, default on — this replaces a three-way preview setting, since "only if full-resolution preview" was a crude form of the same comparison), **unrenderable-edits fallback** (show labeled export/preview [default] / skip — governs the cases where edits exist but no route can render them: LR unavailable, unordered conflict), **track JPEG exports for cleanup** (default on — the inventory switch, with its delete-on-off / instant-index-rebuild-on-on contract), **on-screen status markers** (default on — silences routine chrome only, per the honesty rule), **video sound** (default muted), **close-Lightroom-on-screensaver-start** (default off = defer; screensaver-triggered launches only), **look-ahead depth** (default 10, clamped 3–50), **history size** (default 200, clamped 20–1000 — one value governing both how far ← reaches and how long rendered artifacts are retained; replaces the navigator's hard-coded 200), and the copy explaining that a slide may hold while the next photo renders, alongside the measured per-editor render times. Clamps enforced in `main/settings.ts` like the existing numeric settings.
The on-screen marker and the `O` overlay wording land here, covering every non-plain case in the display table.
FUSE/network-mount validation applies to **persisted settings at startup, before any path traversal or scan** (a hung mount must not wedge launch; a recovery screen lets the user remove the folder) as well as to new folder selection.
**Zero-ready cold start**: with everything rendering, an all-RAW library has nothing ready at show start — the show must enter a waiting state ("rendering your library…") and hot-swap slides in as the first renders land (today `startShow` reports "no images" and later updates are ignored because no swappable playlist exists). The waiting state must be **terminal-aware**: when no viable render job remains (editors unavailable, previews inadequate and rendering off, all renders failed), it becomes an actionable "nothing can display with current settings" message naming the setting to change — never an infinite spinner, especially under `--show`. With no render timeout anywhere, this branch is the only thing separating honest patience from a dead end, so it is tested directly.
Gate: headless smoke over a fixture tree covering every row of the display table shows the right artifact with the right marker per setting; flagging a RAW slide records the RAW's source path (not the buffer URL); the export inventory is complete after a scan with no show ever started, and re-scanning is idempotent (no duplicate entries); a batch-flag benchmark over a few thousand siblings completes in a scan-appropriate time; every no-sidecar pair displays its JPEG regardless of classification, with the in-camera verdict producing a `redundant-export` entry and export/ambiguous producing protected `export-only-edits`; the tracking switch is exercised both ways — off deletes automatic entries while manual flags and dismissal tombstones survive, on rebuilds the complete inventory from the index with zero filesystem or exiftool calls; the fixture set's ambiguous rate is logged; a `multi-editor-conflict` renders the newest editor, badges the slide, flags the RAW, and withholds the JPEG from the inventory; the status-markers setting silences corner markers and the render-wait status but provably never the terminal message; a v1 `flags.json` migrates with its entries intact and stamped `manual`; the zero-ready cold start reaches a running show without restart; a focused test drives the terminal branch to the actionable message, never the spinner; a **protocol-boundary assertion** proves browser-decodable sources and contained buffer/preview artifacts load while RAW source URLs are refused (scanner and protocol share `isMediaFile`, so widening one must not open the other); and an **injected startup test** proves a rejected persisted mount reaches the recovery screen with zero `realpath`/`readdir`/`stat` calls against it.

**P4 — Lightroom companion plugin (`apps/lightroom-plugin/`).**
Hand-rolled Lua, file-based job queue (Afterglow writes job JSON into a watched folder; plugin polls via `LrTasks`, imports, forces sidecar read, exports into Afterglow's render buffer, writes result JSON).
**The plugin guards every claim by catalog identity**: before touching any job file it verifies `activeCatalog()` is Afterglow's dedicated render catalog and otherwise ignores the queue entirely — job files and the plugin survive restarts, so without this check a stale job observed while a user's catalog is open would import and `readMetadata()` there, violating isolation. The stale-job/user-catalog restart scenario is gated.
**Zero-dialog operation is a hard requirement** (screensaver runs unattended; any interaction stops it — Tristan, 2026-07-26).
Spike-verified (2026-07-26) constraints the implementation builds on:
- The `readMetadata` prompt fires even for fresh imports but is **durably suppressed** via LR prefs: `doNotShowPrompts` must contain `AgLibrary_readMetadata` with `AgLibrary_readMetadata = "read"` — onboarding verifies/pre-seeds these keys (verified: first call blocked on the dialog, every later call silent and instant).
- The **"AI Updates Recommended" dialog is solved** (spike-verified 2026-07-29): with `AIUpdateWarning_shouldUpdateAffectedPhotos = true` in LR prefs, a **fresh** import of an AI-mask CR3 (+`.xmp`+`.acr`) exported unattended with zero dialogs, and the unattended output is pixel-identical (RMSE 0) to the attended spike's export of the same photo. Onboarding verifies/pre-seeds this key alongside the metadata-read keys. Mask fidelity was proven in the same session: stripping the XMP's `crs:MaskGroupBasedCorrections` block changes the render (RMSE 2.1 %), while removing the `.acr` sidecar changes nothing — mask corrections render from RAW + XMP alone, so `.acr` files matter only as edit-change signals (they still count as dependencies in the render identity), never as render inputs. No AI-mask setting, exclusion, or mask-less fallback ships.
- SDK plumbing (all learned the hard way): catalog writes need a fresh `LrTasks.startAsyncTask` per job **and** a `{ timeout }` on `withWriteAccessDo`; use `LrTasks.pcall`, never plain `pcall`, around anything that yields; `LrForceInitPlugin = true` or the init script may never run; job-file claims must be **verified atomic** (an unverified claim rename caused a runaway respawn loop in the spike — claim, confirm the claim succeeded, and de-duplicate in-process before processing).
**Plugin throughput is measured** (2026-07-29 spike, prototype v0.3 on home-pc): warm single-photo round-trip (import → `readMetadata` → export at 2560 px) 5.4–6.4 s; batch of three 14.8 s (~4.9 s/photo — LR parallelizes renders internally, so batching moment members into one job is worth keeping); first photo after LR launch ~9.6 s; LR process start → watcher operational ~12 s. Comparable to darktable-cli on the same machine — the CR3 era paces like the rest of the library. The prototype also validated the verified-claim job protocol (claim rename confirmed + in-process dedup — the v0.2 unverified claim reproduced the runaway respawn the first spike hit) and `LrInitPlugin`/`LrForceInitPlugin` auto-start (no menu interaction; the real plugin inherits this).
Afterglow side: LR discovery; launch-minimized **with the dedicated render catalog** on show start when LR-owned jobs are pending; graceful close of Afterglow-launched instances on show end; defer jobs (surfaced honestly) whenever a user's own LR session is open. **The close path needs a real mechanism** (spike evidence: two `CloseMainWindow` requests over ~75 s did not exit an idle LR — WM_CLOSE to the main window is not enough). Design it in this phase; because the render catalog is disposable by design, an Afterglow-owned instance that ignores the graceful path **may** be force-closed after a generous grace period — a **user-owned session is never force-killed**, full stop.
**Crash recovery**: if startup finds an LR instance already running against Afterglow's own render catalog (an orphan of a crashed run — neither user-owned nor launched by this run), the new run **adopts** it: stale job claims are reset, pending job files reconciled, and if adoption fails the instance is closed gracefully; the crash-restart path is gated.
**The render catalog is bounded and disposable**: it is Afterglow-owned throwaway state — when the render catalog is not open in any LR instance **(a precondition for every reset trigger — bound exceeded or plugin-version change alike; an upgrade arriving while a crashed run's orphan still holds the catalog waits for adoption/close first, and that recovery path is gated)** and a trigger fires (bound exceeded: photo count or on-disk size incl. previews; or plugin version change), Afterglow deletes the **complete catalog file family** — `.lrcat`, its `.lrcat-data` companion, preview folders, and any helper files beside them — and starts fresh (imports are cheap metadata operations, so a reset costs only re-import on next use). It never grows indefinitely, and because no durable per-photo Lightroom state is ever relied upon, a reset forfeits nothing.
Gate: end-to-end on home-pc — start a show over a library containing a crs-edited CR3, **including an AI-mask photo**, and watch the look-ahead scheduler render and display them with **zero dialogs and zero manual interaction** (the pref keys are spike-verified; the gate re-proves them through the real plugin and onboarding path).
The **isolation branch is gated too**: with a user's own catalog open in LR and the setting off, verify jobs defer — no import, no `readMetadata()`, and Afterglow neither closes nor force-kills that instance. With the opt-in setting on, verify the graceful close on a screensaver-triggered launch, that manual launches never close a user session, the deferral fallback when the close is blocked, and that force-kill never occurs. The **catalog bound is gated too**: exceed it with LR closed and verify the catalog + previews are deleted and the next job re-imports into a fresh catalog.

**P5 — Release.**
**Plugin distribution**: the `.lrplugin` ships inside the app package (electron-builder `extraResources` — today only `dist/**` + `package.json` are packaged), and on first run Afterglow **copies it to a stable per-user location** (`<userData>/lightroom-plugin/`) and refreshes that copy on version change — onboarding registers the stable path, never the bundle path (the portable build unpacks `extraResources` into a temp dir that vanishes on exit, which would silently break LR's registration). Onboarding: settings shows the stable path + "add it in LR: File → Plug-in Manager → Add" with per-editor status; LR has no headless plugin install.
**exiftool distribution**: the per-platform exiftool payload (P1's bundling decision) ships the same way — `extraResources`/`asarUnpack` per platform for NSIS, portable, AppImage, and deb — and the clean-install gate exercises embedded-preview extraction and batched sibling classification from each packaged build (nothing in `dist/**` carries it today).
Queue-access ridealong (see `docs/Feedback_v0.6.md`): a settings-screen "Flag queue" button with `Q` accepted there, on new count/change IPC. **The button counts manual flags**, with automatic entries shown as a secondary figure — an unqualified total would read "Flag queue (14,382)" on the family library and bury the tester's own flags. The queue window gains filtering by source and category for the same reason; that is more than the feedback doc's original button, and it is the minimum that keeps the window usable once the inventory exists. Its per-type badges adopt **mobile's fixed state-model palette** (`docs/STATE_MODEL.md` rule 2: edit-blue, organize-amber for move, cull-red for delete, one hue per kind, never the accent) so the same colour means the same thing on both surfaces; automatic entries are annotation-plane and stay neutral.

## Risks

- **The LR suppression keys are undocumented Adobe internals** (`doNotShowPrompts`, `AIUpdateWarning_shouldUpdateAffectedPhotos`) — an LR update could rename or reset them. Onboarding verifies/pre-seeds them on every run rather than once, and the P4 gate re-proves dialog-free operation through the real plugin; if a future LR breaks them, the failure mode is deferred jobs with an honest status, never a hung show.
- **Sibling misclassification** → display is classifier-independent (every no-sidecar pair shows its JPEG), so a wrong verdict never changes what plays; the badged, recorded verdict is correctable in v0.7, and `ambiguous` is protected by default so the failure mode is a stale inventory row rather than deleted work.
- **CI cannot run editors** → renderer interfaces + fakes in CI; live-render smoke is a documented manual step on the two known machines.
- **CR3 embedded preview is only 1620×1080** → below adequacy on 1440p, so unedited CR3s render rather than showing a soft preview; the plugin covers the edited ones.
- **Slow relay to home-pc for remote dev** → prefer running scripts on the machine (SSH) over transferring files.
