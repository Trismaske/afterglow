# Repository review — 2026-07-18

Review of the full repository and the in-progress implementation of
[Plan_20260718.md](Plan_20260718.md). This began as a discussion document; its
recommendations were accepted for implementation later on 2026-07-18. The
decision record and implementation ledger below supersede the original open
questions while preserving the evidence that led to them.

## Decision record and implementation ledger

- **Release destination:** GitHub Releases only. GitLab is deferred until
  further notice; no GitLab pipeline or remote is being added.
- **Release shape:** one public m0.6 version/tag, with six internal gates. No
  tester-visible split version.
- **Decision invariant:** tapping the active Keep, To edit, or Cull verdict
  clears to `unreviewed`. The deterministic default is used instead of hidden
  previous-state history. Best/favourite remain orthogonal metadata.
- **Group completion:** late tester feedback removed the automatic Reconsider
  detour. A group completed during review advances to the next unfinished
  group; an already-completed group opened deliberately remains browsable.
- **Trash safety:** implemented a local Android 11+ MediaStore module using
  `createTrashRequest`; both removal entry points use it, cancellation and
  failure differ, API < 30 has no permanent fallback, and the cull action is
  disabled there. Samsung trash/restore is still a manual release gate.
- **Persistence/schema:** implemented FIFO captured-snapshot writes with a
  blocking retry alert and commit-only durable-state advancement; migrations
  are exclusive transactions and have fresh/v5/failure/newer-version tests.
- **Editor diagnostics:** implemented explicit `image/*`, content-URI
  validation, and retained EDIT/VIEW errors. No speculative `<queries>` entry
  was added; native chooser work is conditional on Samsung evidence.
- **Favourites/stats foundation:** implemented batched favourite/unfavourite
  native actions, verification API, durable queue/error states, exact lifetime
  event timestamps, lifetime aggregation, and current/longest streak math.
- **Repository hardening:** Electron moved from 37.10.3 to 43.1.1; root lint
  and format gates exist; root JS/Metro and clean native Android CI exist;
  Actions are SHA-pinned; releases verify tag/version/artifacts and publish
  SHA-256 checksums.
- **Snapshot validation:** duplicate/missing/invalid state, membership, best,
  compare and cursor corruption are rejected with regression coverage.

The remaining work is the feature implementation already described by the
m0.6 plan plus emulator/Samsung acceptance. Those are now staged behind the
internal gates in [Plan_20260718.md](Plan_20260718.md), rather than unresolved
review recommendations.

## Executive assessment

The baseline reviewed here was thoughtfully structured: the shared core is
pure and well tested, desktop has a strong Electron security model, and mobile
keeps platform bindings separate from most pure logic. The initial review run
passed 441 unit tests.

It was **not ready to build or release at review time**. The most important
finding was a mismatch between the recoverable-trash promise and Expo's
permanent-delete implementation, plus incorrect editor/favourite assumptions.
The remediation ledger above records the implemented corrections. The approved
m0.6 feature work and locally executable internal gates are now complete. The
remaining Samsung-specific checks are explicitly assigned to tester acceptance.

## Release blockers — add before m0.6 implementation continues

### P0. Replace permanent deletion with the promised trash operation

Evidence:

- `apps/mobile/src/lib/media.ts` calls legacy
  `MediaLibrary.deleteAssetsAsync` and describes the result as system trash.
- The installed Expo SDK 57 implementation requests
  `MediaStore.createDeleteRequest`, then calls `ContentResolver.delete`.
- Android documents `createDeleteRequest` as permanent deletion and
  `createTrashRequest(..., true)` as the recoverable trash operation.
- The incorrect recovery promise is repeated in the Home copy, cull-list copy,
  README, product plan, assumptions, and source comments.

Action:

1. Add one small Android MediaStore-actions module and use
   `MediaStore.createTrashRequest` for the whole staged batch on API 30+.
2. Route both destructive entry points through it: cull-list confirmation and
   the edited-copy "Cull original" choice.
3. On API < 30, either disable in-app deletion or state clearly that deletion
   is permanent and require a distinct, explicit confirmation. The conservative
   default is to disable it.
4. Distinguish user cancellation from operational failure. The current wrapper
   catches every exception as "cancelled", which hides genuine failures.
5. Verify on the Samsung test device that a trashed photo appears in Gallery's
   trash and can be restored. Add this to the release checklist.
6. Correct all user-facing and technical documentation only after the native
   path is verified.

Primary references:

- [Android shared-media guide](https://developer.android.com/training/data-storage/shared/media)
- [Android MediaStore API](https://developer.android.com/reference/android/provider/MediaStore)
- [Expo SDK 57 MediaLibrary](https://docs.expo.dev/versions/v57.0.0/sdk/media-library/)

### P0. Make session persistence failure-safe before adding more state

`SessionContext.persist()` assigns `lastStatesRef.current = after` **before**
the SQLite transaction succeeds. If `persistDecision` fails, a later retry sees
no changed photo states and can save a fresh snapshot while leaving the durable
`photos` rows stale. This contradicts the repository's "SQLite is durable
truth" invariant.

Action:

1. Advance the last-persisted state only after the transaction commits.
2. Serialize state mutations/persistence explicitly and define rollback or
   retry behavior for a failed write.
3. Surface a blocking error to the user when a decision was not durably saved;
   do not silently continue.
4. Add failure-injection tests around kept, to-edit, culled, clear-decision,
   favourite, and resume flows.

### P0. Make schema migrations atomic and test upgrades

`migrateDatabase()` executes each multi-statement migration and the
`user_version` update as a raw batch, despite the module comment claiming a
transaction. A partial failure after an `ALTER TABLE` but before the version
bump can make the migration fail forever on restart. m0.6 necessarily adds
favourite/stat fields, so this is the right release to fix the runner.

Action:

1. Run each migration through an exclusive transaction, using the transaction
   object for every statement and updating `user_version` last.
2. Keep shipped migrations immutable; make new migrations idempotent where
   practical.
3. Add upgrade fixtures/checks for a real v5 database, a fresh database, and an
   intentionally interrupted migration.
4. Back up or export the tester database before the first m0.6 on-device
   upgrade test.

Reference: [Expo SQLite transactions](https://docs.expo.dev/versions/v57.0.0/sdk/sqlite/).

### P0. Revise the editor-launch investigation

The plan's leading theory—missing Android 11 `<queries>` entries—is contradicted
by both Android's documentation and the installed `expo-intent-launcher` code.
Direct `startActivity()`/`startActivityForResult()` does not require package
visibility, and Expo launches the intent directly without first calling
`resolveActivity` or `queryIntentActivities`. Adding `<queries>` is therefore
unlikely to fix this failure.

Action, in evidence-first order:

1. Preserve and show the exact exception code/message and the attempted URI,
   action, MIME type, and flags in a copyable diagnostic view (avoid logging
   private file paths outside an explicit diagnostic action).
2. Add `type: 'image/*'` to EDIT and VIEW and test it on Samsung; Expo correctly
   uses `setDataAndType` when both values are present.
3. Validate that `getAssetContentUriAsync` returns a resolvable content URI for
   the affected asset and that a simple VIEW intent opens it.
4. If Expo's launcher still fails, implement a small native chooser using the
   same content URI and read/write grants. Only add `<queries>` if new code
   actually queries installed handlers.
5. Keep the Samsung on-device test as the acceptance gate.

Primary references:

- [Android package-visibility use cases](https://developer.android.com/training/package-visibility/use-cases)
- [Expo SDK 57 IntentLauncher](https://docs.expo.dev/versions/v57.0.0/sdk/intent-launcher/)

### P0. Decide and implement the actual release destination

Current state:

- `origin` is `git@github.com:Trismaske/afterglow.git`.
- `desktop-v*` and `mobile-m*` tags publish only through GitHub Actions to
  GitHub Releases.
- Work is on `initial`; `main` still contains only the initial project state.

Action:

1. Confirm whether "GitLab release" is intentional or whether the existing

2. If GitLab is intentional, establish the GitLab project/remote and release

## Important m0.6 design corrections

### P1. Reframe favourites around what SDK 57 actually provides

Expo SDK 57 **does** expose Android favourites through the new
`Asset.setFavorite(true)` API. The legacy API used by the rest of this app does
not expose Android favourites. Expo's new method requests write permission for
an asset and updates `MediaStore.IS_FAVORITE`; it does not provide the plan's
one-confirm batched queue.

The native module is still justified if one batched confirmation is a hard
requirement, but the plan should say so accurately. The module can share the
MediaStore-actions boundary proposed for trash.

Action:

1. Keep favourite state orthogonal to the review state, for example
   `none -> queued -> applied`, with timestamps and an error/retry state.
2. Apply a batch using `MediaStore.createFavoriteRequest` on API 30+ and verify
   actual `IS_FAVORITE` values before marking rows applied.
3. Make applying idempotent and resumable after cancellation, process death,
   or a partial failure.
4. Test Samsung Gallery explicitly. Expo warns that third-party galleries may
   maintain a separate favourites list and may ignore MediaStore's value, so
   the plan must not promise Samsung/Google Photos behavior until verified.
5. Decide what happens when a favourite is cleared after it was applied to the
   gallery, and whether that produces an "unfavourite" queue.

### P1. Define one consistent per-photo decision model

The in-progress `DeckSession.unkeep()` is only half of feedback item 7 and is
not yet called by the mobile app. Existing deck "Needs edit" toggles only the
app-side flag while the core photo can remain `unreviewed`; this does not yet
meet "to-edit implicitly keeps the photo." Favourites introduce the same
problem because they also imply kept.

Required semantics to settle before wiring UI:

- active Keep tapped again: `kept -> unreviewed` and reopen the group;
- active To edit tapped again: clear the edit flag but remain `kept`;
- active Cull tapped again: restore to `kept` (or explicitly choose
  `unreviewed`, but use one rule everywhere);
- marking To edit or Favourite on an unreviewed photo: atomically make it kept;
- clearing Keep on a starred/favourited photo: define whether ★/heart remains,
  clears, or prevents the transition;
- singles and grouped photos must follow the same rules.

Add core transition tests, SessionContext orchestration tests, persistence
tests, and UI acceptance checks for every row above.

### P1. Extend the database before promising the stats card

The existing schema can derive reviewed/culled/reclaimed totals and current
streaks, but it cannot reliably distinguish "edit completed" from a normal
keeper that became `done`. `to_edit_at` is retained after toggling the edit flag
off, so it is not an accurate completion record. Favourites also have no schema
yet.

Action:

1. Define the exact metric semantics first (unique photos vs. events, and how
   restored/deleted/re-reviewed photos count).
2. Add durable event or completion timestamps for edits and favourites.
3. Compute current and longest streak from one tested pure helper and a single
   ordered day query.
4. Test totals across session replacement, re-decisions, delete cancellation,
   and repeated favourite application.

### P1. Add native Android validation before a tag can release

The regular mobile CI only typechecks, runs JS tests, and exports a Metro
bundle. It never runs Expo prebuild or Gradle. Today the first clean native
compile can therefore happen only after a release tag triggers the release
workflow. That is too late once m0.6 adds MediaStore native code.

Action:

1. Add a non-release Android CI job (or a manually gated release-candidate job)
   that runs clean prebuild and `assembleRelease` without publishing.
2. Add unit tests for native URI conversion and result handling where possible,
   plus emulator/device integration checks for trash and favourites.
3. Keep the Samsung checklist as a required manual gate for editor launch,
   gallery trash, gallery favourite, pinch hand-off, and upgrade-in-place.

### P1. Add deterministic release/version checks

The candidate still reports mobile `0.5.0` in `app.json` and `package.json`,
with Android `versionCode: 2`. The workflows accept any matching tag and do not
verify that the tag, app version, version code, artifact name, and source commit
agree.

Action:

1. Add a release-preflight script that verifies the tag/version mapping and a
   monotonically increased Android version code.
2. Fail on missing expected artifacts; publish SHA-256 checksums.
3. Run the exact clean-install command and all verification commands from the
   tagged commit before upload.

### P1. Stage the oversized release even if it keeps one version number

m0.6 currently combines feedback fixes, a deck/singles refactor, two new native
MediaStore operations, schema changes, stats, performance work, gesture work,
and a design pass. That is a large regression surface for a photo-deletion app.

If the feature-completion decision remains locked, use internal gates:

1. data safety + persistence/migrations;
2. feedback fixes and decision model;
3. singles/deck unification;
4. favourites + stats;
5. measured performance work;
6. clean build, emulator checks, Samsung checks, then release.

Each gate should return to green before the next starts. A split release
(m0.6 feedback/safety, m0.7 feature completion) remains the lower-risk option.

## Repository-wide follow-ups

### Desktop v0.6 blocker: upgrade Electron

`npm audit` reports the pinned Electron 37.10.3 line affected by multiple
current advisories, including high-severity use-after-free and renderer-related
issues. Electron is also pinned separately in `electron-builder.yml`, so both
locations must move together. Upgrade to a currently supported stable Electron
line, then rerun typecheck, tests, build, package, and the headless smoke test on
Linux plus a Windows installer/screensaver pass.

The audit also reports moderate Expo/tooling-chain advisories. Its suggested
automatic "fix" is an invalid downgrade to Expo 46, so do not run
`npm audit fix --force`; track supported SDK 57 patches and triage runtime
reachability instead.

### Release hardening

- Add a root CI job so a core change always runs core tests, both app
  typechecks/tests/build proofs, and `git diff --check` before merge/tag.
- Pin third-party CI actions to immutable commit SHAs before wider distribution.
- Make desktop matrix artifacts explicit and fail a platform job if an expected
  installer is absent; `fail_on_unmatched_files: false` can publish a partial
  release silently.
- Generate checksums and retain build provenance/logs for every release.

### Test and maintainability debt

- Mobile's highest-risk files (`SessionContext`, database store/migrations,
  Home, Deck, Compare) have little or no orchestration/component coverage.
  Extract pure state reducers/use-case functions around m0.6 transitions so
  failure cases can be tested without React Native.
- Add a real lint/format command and CI check. The roadmap says CI includes
  lint, but no lint script or configuration exists.
- `DeckSession.fromJSON` validates only the outer shape. Harden it against
  duplicate IDs, missing states, invalid states, unknown group members,
  conflicting group/single membership, and invalid best IDs before treating a
  snapshot as resumable.
- Break up the largest screens as part of touched-feature work, especially the
  shared deck/singles refactor; avoid a broad unrelated rewrite during m0.6.
- Standardize user-visible handling for async failures. Several focus loaders
  and action callbacks swallow errors or can reject without an actionable UI.
