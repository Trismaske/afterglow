## The F22 spike (measured 2026-08-22, S10e)

Harness: a standalone `BitmapRegionDecoder` benchmark compiled against the platform jar and run on-device via `app_process` (no app build; recipe distills into ANDROID_DEVICE_TESTING.md at close-out).
Files: real S23 camera output — 50MP-mode JPEG (8160×4592), 200MP-mode JPEG (16320×9180), both sizes as HEIC, one 109 MB DNG — plus a 12MP baseline and a 150MP Lightroom re-export as a high-entropy stress case.

**Stage-sized `decodeRegion` patch, gesture-settle scenario (S10e, warm):**

| Zoom | 12MP JPEG | 50MP-mode JPEG | 200MP-mode JPEG | HEIC (both sizes, after warm-up) |
|---|---|---|---|---|
| 2× | ~150 ms | ~100 ms | ~232 ms | 21–31 ms |
| 8× | ~74 ms | ~62 ms | ~164 ms | 8–30 ms |
| 16× / 1:1 | ~57 ms | ~48 ms | ~120 ms | 3–14 ms |

`newInstance` (open + index): 15–28 ms (DNG 221 ms).
DNG serves patches in 113–224 ms via its full-size embedded preview — the same preview every other surface shows for DNG, so the overlay stays consistent.

**Addendum (2026-08-23), the hand-off measurements behind D6:** encoding a stage-sized (9 MB) / mid-zoom (33 MB) patch on the S10e — JPEG q95 34/108 ms, JPEG q100 44/156 ms, PNG 881/3188 ms, lossless WebP 1848/8278 ms.
Lossless file encodes are off the hot path.
Verified in the installed source: expo-image 57's `source` prop accepts a `SharedRef<Bitmap>` (ExpoImageModule.kt:304-321), and `SharedRef` lives in expo-modules-core, so a local module can mint one with no new dependency.

**What the spike settles:**

1. **C1 holds on the floor device for every format on the phone.** Worst real-file patch: ~232 ms (200MP-mode JPEG at 2×). The reported 50MP case: 48–100 ms.
2. **Baseline JPEG region cost is linear in the region's row position** (entropy decode of all rows above it; measured 150→1010 ms top→bottom on the 85 MB stress file, proportionally small on real 12–25 MB camera files). Consequence: the escalation ladder's C2 pivot (`subsampling-scale-image-view`) wraps the **same** decoder and cannot rescue a slow file; the real mitigations — a per-photo decoder instance and patch reuse — belong to C1 equally. C2 remains the ladder's last rung for gesture-integration failures only, not for decode speed.
3. **HEIC is internally tiled: patches are near-free (3–36 ms) after a first decode that costs like a full decode** (0.8–2.5 s software on the S10e; the in-app hardware path is expected to be far faster — S23 gate measures it). Consequence: the pipeline **warms the decoder off the gesture path** (spike amendment 1, phase 4).
4. **A literal "base ≥4096 px" is unachievable**: `inSampleSize` moves in powers of two, so 8160-px sources offer 4080 or a 142–190 MB full decode, nothing between. Resolved by D2's formula (phase 4).
5. **A raised base costs ~35–50 MB per live bitmap** (an ordinary 12MP photo full-res: 45 MB versus ~10 MB stage-sized today). Resolved by D1 (overlay-only) and D7 (byte-budgeted retention).

### Phase 4 — F22: the region-zoom pipeline

The spike de-risked the decode; the grilling (D1–D7, appendix) settled the strategy; this phase is integration.
The two layers: a **base** (the whole image at bounded resolution) carries mid-gesture, a **patch** (the visible region + margin at ≥1 source px per screen px) carries every settled view.

1. **Proof task first (D6):** mint a `SharedRef<Bitmap>` from a local module and render it through the overlay `Image`'s `source` prop (verified accepted, ExpoImageModule.kt:304-321) — contentFit, sizing, and release checked. Passes → zero-copy lossless delivery for bases and patches. Fails → the pre-registered fallback is a JPEG q100 cache-dir temp file (measured 44–156 ms; run-scoped under cache policy), and PNG/WebP stay rejected (measured 0.9–8.3 s).
2. **Native functions** in the `media-store-actions` module: open/close a per-photo `BitmapRegionDecoder`, decode a base, decode a patch (URI + source rect + sample → `SharedRef<Bitmap>`). ARGB throughout (16-bit banding would corrupt keep/cull judgments — G3). Decodes run off the UI thread, single-flight per surface: a newer request supersedes a queued one; in-flight work cancels on photo leave.
3. **The base (D1, D2):** applies **only to the zoom overlay image** on all three surfaces — pager pages and at-rest panes already decode to view size, which is crisp at rest on any device. Sizing: target `T = max(stage long edge in device px, 3840)` (device-adaptive; 3840 covers every mobile display shipped, 4K Xperias included); the base is the **largest power-of-2 sample ≥ T** (8160/16320-px sources → 4080, ~46–50 MB); a source with no sample ≥ T decodes **at full resolution** (a 12MP photo's base is the original — patches never engage for it), under a **~128 MB per-bitmap guardrail** that steps one sample down instead (exists for Compare's two simultaneous panes; a step-down logs unconditionally to `diagLog` with the dimensions — D9). Never a blanket `allowDownscaling={false}` on original URIs (a 200MP full decode is ~570–760 MB).
4. **Warm timing (D3):** the base decode — which for HEIC *is* the warm-up, since its first decode costs like a full decode — starts when the current photo has been **settled for ~400 ms** (dwell-triggered; threshold is a device-pass tunable). Judged photos are warm before a pinch; rapid swiping costs nothing. Current photo only; no predictive neighbour warming. Until the base lands, the overlay shows the stage-size cached image — today's quality, no regression window.
5. **The patch (D4):** engages when the base no longer supplies ≥1 source px per screen px in view; sample is the **largest power-of-2 keeping ≥1 source px per screen px** — never sub-screen, supersampled up to 2× per axis. The ~10 MB target is retired (it conflicts with settle-sharpness by construction); measured worst pre-margin patch is 34 MB. A `diagLog` line reports real patch bytes for the pass.
6. **Pan coverage (D5):** patches decode with a **byte-budgeted margin** — `marginFactor = √(budget / patchBytes)` per axis, capped at 2×, clamped to image edges, **budget ~64 MB** (device-pass tunable). Self-balancing: widest at deep zoom where the base fallback is softest, ~none at the engage boundary where the base is nearly screen-resolution.
   A margin clamped below the 2× cap by the budget logs rate-limited with the factor reached (D9) — raising this budget **slows every patch** (decode time scales with rows covered), so it is never raised without those numbers. Decode triggers: zoom settle, **pan-decay settle** (the `withDecay` glide ends, not finger-up), and debounced (~150 ms) mid-pan coverage exit. The stale patch stays mounted until its replacement lands; patches are keyed on rect + sample so an unchanged view never re-decodes. The device-tuned gesture worklets are untouched.
7. **Retention (D7):** visited bases live in an MRU list capped at **~192 MB total bytes** (device-pass tunable) — typically 4 ordinary photos, self-limiting to 2–3 huge ones, always fitting the guardrail pair; flushed on unit advance. Patches are not retained across photos. Decoder instances reopen on return (15–28 ms measured).
   **Memory pressure (D9):** an `onTrimMemory` signal flushes retention to current-only — speed degrades (a re-warm is 170–420 ms), never sample quality — and always logs loudly with what it dropped; LRU evictions aggregate per session. No user-facing memory setting and no static RAM scaling (a knob nobody can reason about; scaling down hurts the prioritized pan UX); budget raises are device-pass decisions made with the D9 log numbers in hand, retention being the pre-blessed candidate.
8. **Format fail-soft:** any format `BitmapRegionDecoder` opens gets the pipeline (JPEG, HEIF, and DNG via its full-size embedded preview — all measured); a failed `newInstance` logs once to `diagLog` and leaves the overlay on the stage-size cached image. No format allow-list.
9. **Correct the wrong header comments** claiming full-res decode: DeckScreen.tsx:100-106 and its duplicates in PhotoViewer.tsx and CompareScreen.tsx — they describe the pipeline this phase actually builds.
10. **Escalation ladder, amended by the spike:** tester unhappy *mid-gesture* → raise `T`; unhappy *after settle* → a patch bug, fix it; C2 (tiling library) is now **only** the rung for gesture-integration failure, since it shares the decode engine (spike conclusion 2).

## Autonomous decisions (appendix)

**All entries human-vetted at the close-out grilling (2026-08-26, 13 questions, zero rejections).** The grilling's riders: the zoom fail-soft notice (entry 19, built), `FLICK_MIN_VELOCITY` joined the S23 tunables, the shared ZoomSurface refactor parked in docs/TODO.md for the m0.9 pre-build grilling, and two on-device probes confirmed mirrored EXIF orientations are unmintable on the test hardware. The entries remain below as the release record until this doc retires at ship.

1. **(phase 4) EXIF orientation architecture.** The decoders work in sensor space while every surface displays the rotated image (all four seeded S23 shots are orientation=90 — this is the everyday case, found on the first device run). Chosen: `open` reports the rotation; the native side rotates every decoded bitmap to display orientation (one transient copy, ≤ the bitmap's own size); the display↔sensor rect mapping lives in `lib/regionZoom.ts` as pure, unit-tested functions (patch rects align to sample multiples in SENSOR space, where the decoder's grid lives). The alternative — orientation-aware geometry throughout JS with unrotated bitmaps — would smear rotation cases across every consumer.
2. **(phase 4) Density enters sample selection only.** RN layout reports dp; D4's "≥1 source px per screen px" is a physical-pixel promise — without `PixelRatio`, every patch looked unnecessary on a 3× screen (measured on device: `plan=null` at 2.5×). Chosen: geometry stays dp-consistent (stage, transforms, placement); `PixelRatio.get()` multiplies into the spp used for sample selection and into the D2 base target. Device-adaptive as D2 intended.
3. **(phase 4) On-device proof results (S10e, release build).** `SharedRef<Bitmap>` **renders** through expo-image's `source` (D6 proven visually; the q100 fallback stays unused). Bases decode and paint on all four tiers — 50MP-mode JPEG 852–1211 ms, 150MP JPEG s4, HEIC (its warm-up), DNG via embedded preview with correct rotation. Quirk for the record: expo-image fires no `onLoad` for SharedRef sources — diagnostics must not rely on it. Deep-zoom patch decode is unit-tested end-to-end but not yet exercised on device: the S10e denies `sendevent` (no scripted pinch) and the deck's double-tap 2.5× is *correctly* served by the base alone — a real pinch past ~4.5× is a **device-pass agenda item** (watch for `[perf] zoom patch` lines).
4. **(phase 4) The tester crash + softness, root-caused from the sink (2026-08-24).** Two defects in the delivery path, both fixed: (a) the native module never **registered** `RegionBitmapRef` (`Class(...)` in the definition), so the JS-side object had no SharedObject prototype — `.release()` was `undefined` and every patch swap / zoom-out / eviction crashed the release build with a fatal TypeError; every release call is now optional-chained (`release?.()`) so a missing method can only ever degrade to GC-paced reclamation, never a crash. (b) The overlay `Image`s did not set `allowDownscaling={false}`, so expo-image's Android default re-downscaled the delivered bitmaps to the view's layout size — silently discarding exactly the pixels the pipeline decoded (the F22 root cause re-imported through the delivery). The sink also proved patches decode under real pinches (`zoom patch … s1 34MB 744ms`), and surfaced a 150MP mid-zoom patch at 3.8 s — margin cost on high-entropy JPEG, added to the pass agenda.
5. **(phase 4, Tristan 2026-08-24/25) Dynamic per-photo max zoom.** A fixed 16× stopped *before* 1:1 on a 200MP photo (1:1 ≈ 18× on the deck stage) while deep fixed maxima on 12MP are mush. New rule (`maxScaleFor`): `clamp(2.5 × scale-at-1:1, 24, 48)` per photo, from its real resolution and the surface's stage — Compare takes the max of its pair; unknown resolution keeps the floor. Tristan retuned all three numbers (2026-08-25): headroom 2 → 2.5, floor 16 → 24 (the 12MP focus-and-sharpness check always rode the old max, and with downscaling off the same gesture deserves more real depth), ceiling 40 → 48 (the 200MP tier lands ~44.6). All three stay device-pass tunables. The patch pipeline keeps the whole range honest.
6. **(phase 4, tester recording 2026-08-25) Deep-zoom flashing + pinch collapsing onto one finger — the host-view gesture class.** Frame analysis of the S10e recording showed the framing leaping between consecutive frames with two fingers down, starting exactly at patch-engage depth. Cause: every patch mounted/unmounted an Image inside the intercepting gesture detector's subtree mid-touch — the deck's documented "cannot survive an inserted host view" class — breaking RNGH's pointer tracking (pinch center collapses to one finger, pan re-anchors) and flashing on every swap. Fix: a **permanently stable view tree** — the base and TWO patch buffer slots are always mounted on every surface and only props ever change; a new patch lands in the older slot z-ordered above, the previous retires ~250 ms after the new one painted (no flash), and buffer application defers to a gesture-quiet poll tick so 30 MB texture uploads never jank an active gesture. The deck's identity gate became prop-gating (sources go undefined) for the same reason.
7. **(phase 4, tester recordings 2-5, 2026-08-25) Settle flashes/shake, in-photo tearing, and slow sharpening — three coupled fixes.** The sink showed ~4 patch decodes per second AT REST with rects jittering ±1 px: `withDecay` creeps sub-pixel for seconds after a glide, and the exact-rect dedup re-decoded (and re-applied, and re-retired) endlessly — the settle flashes and shake. The in-photo tearing had a second cause: Android's HEIF `BitmapRegionDecoder` snaps region origins to its internal 512-px tile grid without adjusting the output, so non-tile-aligned rects return visibly displaced content **(assumed from the recording's shift signature — the device retest confirms)**. Fixes: (a) patch rects now align outward to a 512 sensor-px grid (`PATCH_RECT_ALIGN`) — defeats the HEIF snap and quantizes plans so creep yields identical rects; (b) dedup became **coverage-based**: only coverage loss or a sharper sample warrants a decode; (c) per the tester's ask, decodes now run **speculatively during the gesture** (single-flight, newest viewport, stash-and-apply at the quiet tick) so the sharp patch lands almost immediately at settle instead of quiet-window + decode later. Alignment can add up to 511 px per edge over the margin budget — bounded, logged.
8. **(phase 4, tester recording 6, 2026-08-25) Live sharpening + the at-rest snap.** (a) The "high-res only after settle" limit fell: with the stable view tree an apply is a prop update (gestures untouched), and upload cost scales with patch size — so patches at or under `MIDGESTURE_APPLY_MAX_BYTES` (~24 MB, tunable) now apply IMMEDIATELY mid-gesture. Deep zoom — smallest patches, softest base — sharpens live while panning; only big mid-zoom patches still wait for a quiet tick. (b) The residual at-rest snap ("only at rest does it snap" — the apply itself): RN snaps layout coordinates to the pixel grid, and a deep-zoom scale magnifies that snap into a visible content jump versus the base. Patch slots are now positioned by float-exact transform translation instead of `left/top` layout.
9. **(phase 4, tester recording 7, 2026-08-25) Deep-zoom shimmer + mid-zoom decode contention.** The sink showed two regimes. Deep zoom: tiny patches (~6 MB, 60–130 ms) whose coverage was bound by D5's 2× axis cap while the byte budget sat ~90% unused — every small pan exited coverage, and the decode→apply→retire cycle oscillated regions sharp↔soft (the perceived "drift"/shimmer). The cap is now `PATCH_MARGIN_AXIS_CAP = 3` (tunable): ~9× viewport coverage when the budget allows, decodes a few hundred ms. Mid-zoom on the 150MP tier: 60 MB patches decoding 5.5 s CONCURRENTLY with the 5.5 s base decode of the same file (entropy-stream contention doubling both). Two gates: patch decodes wait for the photo's base decode to finish, and over-threshold (>`MIDGESTURE_APPLY_MAX_BYTES`) patches never decode mid-gesture — they'd hold the single-flight pipeline for seconds and arrive stale; they decode at the quiet tick, with the base carrying the gesture.
10. **(phase 4, tester recordings 8–10, 2026-08-25) Focal-anchored zoom — the zoom-out tracking fix.** The pinch worklets only ever wrote `scale`; the translation stayed fixed while the scale moved, so the content under the fingers slid away — algebraically inevitable (`t` must scale with `s` even for centre-anchored zoom), latent at 16×, violent at the new 24–48× ("zoom out completely loses the photo"; zoom-out-then-in returning correctly was the giveaway — the error is symmetric). Fix in the PURE layer: `panFrame` gained `anchorScale` + the stage centre and now computes `t = F − c − (s/s_a)(F_a − c − base)` — the pan is the one translation writer and fires on every touch frame, so this yields true focal-anchored pinch zoom (content under the fingers stays locked) with zero new writers and zero gesture-structure changes; with constant scale the algebra reduces exactly to the m0.8.6 behavior (all 29 prior gesture tests pass unchanged; 3 new compensation tests). Rider: `MIDGESTURE_APPLY_MAX_BYTES` 24 → 12 MB — the margin-cap raise made live uploads heavy enough to jutter a pan. The one-off "reset to no zoom" report stays under observation: plausibly the scale-1 floor under a hard outward pinch, which focal anchoring makes far more controllable.
11. **(phase 4, tester recording 11, 2026-08-25) The gesture unification — root cause, not another patch.** The tester's "sometimes it zooms to my fingers, sometimes it strays" was the two-tracker design's inherent failure: a pinch tracker owned scale, a pan tracker owned translation, and whether a pinch was focal-anchored depended on whether the PAN gesture had happened to activate. Per the tester's directive (simplify to the solved-problem shape; the researched reference is react-native-zoom-toolkit's pinchTransform — the library itself cannot mount under this app's detector and worklet constraints, so its algebra was adopted), the two trackers, the engagement gate (`PINCH_ENGAGE_DELTA`), `pinchFrame`, `panFrame`, `pinchGain`, and the `pinchZoomed` flag all collapsed into **one** `zoomTouchFrame`: scale from the raw finger span, translation from the raw focal, both off a single anchor taken at every touch-set change — `r = span/span_a; s = clamp(s_a·r); t = F − c − (s/s_a)(F_a − c − t_a)` per touch frame. Scale and translation can never disagree; a pinch is focal-anchored from its first frame; quick-scale immunity is by construction (no span with one finger); the walking-pan continuity carries over (re-anchor is the identity). Net-negative pure code, 10 scenario tests ported/added. The engagement gate's removal means span wobble now breathes the scale a percent or two with content locked under the fingers — a named device-pass judgment. Drivers: deck/viewer stage pinch (≥2 fingers; one finger belongs to the pager) and overlay pan (2 fingers unconditional, 1 finger on activation) — mutually exclusive per stream via the overlay's pointerEvents; Compare single-driver on its pan. **Coordinate-space rider (recording 12):** the first cut read the focal from WINDOW coordinates while the centre was stage-local — the stage's window offset entered the translation scaled by (stretch − 1), so pans were perfect (r = 1 cancels it) while every slow zoom-in drifted the photo downward. The touch reads switched to view-local x/y, which share the stage origin and are stable because every zoom gesture attaches to an untransformed view (the transformed layer would feed back — warned in the type's doc).
12. **(phase 4, tester recording 13, 2026-08-25) Stream arbitration — the per-photo first-pinch freeze and the fighting pan.** The sink showed ~no pipeline activity during the freezes, killing the render theory; the pattern (every freeze on a stream STARTING at scale 1; the smallest photo fine) located both holes in gesture arbitration. (a) The unified driver zoomed from the first touch frame — BEFORE the pinch gesture activated and claimed the stream from the pager's native scroll — so a slow pinch with any horizontal component let the pager steal the stream mid-zoom (fingers keep moving, nothing updates; the old code was immune only because it didn't zoom until activation). The stage driver now requires activation, restoring the proven claim semantics. (b) When zoomed, both the stage pinch and the overlay pan can receive the same stream through the shared interceptor; the inactive stage handler re-anchored the ONE tracker every frame, freezing the overlay's single-finger pan into identity frames ("it's not listening"). An `overlayOwnsStream` claim now stands the stage handlers down completely for overlay-owned streams, the overlay's finalize releases the claim and owns the snap-to-1, and both drivers reset their anchor on `onTouchesCancel` so a stolen stream never leaves stale state.

## Decisions settled in the pre-build grilling (2026-08-23)

All nine vetted one-by-one with Tristan; the measured basis is the spike section above.
The same grilling settled the late feedback items F31–F32 (G12–G13, slotted to m0.9 — see [Feedback_m0.8.7-m0.9.md](Feedback_m0.8.7-m0.9.md)); they add nothing to this release's scope.
Quality mandate stated for the record: highest rendering quality and pan/zoom feel win over memory wherever they conflict.

| # | Decision | Choice | Why |
|---|---|---|---|
| D1 | Base scope | Raised base on the **zoom overlay only**; pager pages stay view-sized | View-sized pages are already crisp at rest on any device; raising them multiplies ~35–50 MB by up to 21 mounted pages for zero visible gain |
| D2 | Base sizing | `T = max(stage long edge, 3840)`; largest power-of-2 sample ≥ T; full-res original when no sample reaches T; ~128 MB per-bitmap guardrail | Device-adaptive (checked: 3200 px is 2026's ceiling, 3840 the all-time 4K-Xperia ceiling); dissolves 4096-vs-4080 (a formula, not a constant); ≤12MP photos get pixel-perfect bases and never need patches; the guardrail exists for Compare's two panes |
| D3 | Warm timing | **Dwell-triggered** (~400 ms after photo settle), current photo only; base decode doubles as the HEIC warm-up | Judged photos are warm before a finger reaches the stage; rapid swiping pays nothing; per-settle warming is churn, zoom-intent-only bets first-zoom sharpness on unmeasured hardware HEIC speed |
| D4 | Patch sampling | ~10 MB target **retired**; largest power-of-2 sample keeping ≥1 source px per screen px — never sub-screen | The target and settle-sharpness conflict by construction; round-up can be no better than the base where the patch engages; measured worst is 34 MB pre-margin |
| D5 | Pan coverage | **Byte-budgeted margin** (~64 MB): √(budget/patchBytes) per axis, cap 2×; decode on zoom settle, decay settle, and coverage exit | Margin need and margin cost both invert with depth, so a budget is self-balancing — widest at deep zoom where the base fallback is softest; no-margin means a sharpen pop every shove; fixed 2× spends 136 MB where it is invisible |
| D6 | Delivery | **`SharedRef<Bitmap>`** zero-copy (proof task opens phase 4); JPEG q100 temp file pre-registered fallback | Verified: expo-image 57 accepts it, `SharedRef` is expo-modules-core (no new dependency); measured: lossless file encodes cost 0.9–8.3 s, q100 adds ~100–300 ms per patch |
| D7 | Base retention | **MRU by bytes** (~192 MB), visited photos only, flushed on unit advance; patches never retained | Tracks actual movement, so chronological-backwards walks and middle-out wandering stay warm without predictive churn; a count-based cache either misses rotations or decodes neighbours nobody zooms |
| D8 | F29 prompts + last flags | Prompt semantics locked (remember-either-answer per direction, "Leave open" declines); fly-vs-snap and the F28 label fallback stay device-pass agenda items | The copy is fully determined by G10's semantics; the two visual calls need real pixels and would be re-litigated at the pass if guessed now |
| D9 | Budget-edge behavior | Fixed budgets + `onTrimMemory` retention flush (speed degrades, never quality); four exhaustion log lines (guardrail step-down unconditional, margin clamp rate-limited, evictions aggregated, trim flush loud); no user setting, no static RAM scaling; raises are pass decisions made on the logged numbers | A memory knob is unreasoned-about (G7 precedent) and static scaling has no winner (high-RAM devices are compute-rich; scaling down degrades the prioritized pan UX); the trim signal reacts to real pressure instead of a guess. Raising the margin budget roughly doubles patch decode latency, so no budget is raised blind |
