# Feedback — 2026-07-23 (third tester round)

Against **mobile m0.6** (app version 0.6.0). No desktop feedback this round.
Tester notes verbatim, numbered for the plan's references; every item is
answered in [Plan_20260723.md](Plan_20260723.md).

1. there is a long notice when starting a new session, that almost seems to
   just say that nothing will be lost. Is it really necessary? What are the
   actual negative effects of starting a new session when one is already in
   progress, if any?
2. in a session, if all the photos are in groups, and there are no singles, it
   still shows the singles "group" with 0 photos. Is it okay to just hide it
   if there are no photos?
3. Should be called favorite queue (similar to edit queue) instead of gallery
   favorites
4. Add a history section, showing past decisions on photos that have not yet
   been deleted
5. In singles view, should go to next photo after decision is made
6. in group view, don't disappear a photo after selecting cull, just show its
   state, and cull everything at the end of a session
7. day progress screen, counts aren't accurate and not all are useful. In
   groups doesn't show a count for current groups or completed groups. Kept
   vs done?
8. should we still show old groups when going back into a completed day?
9. videos not included, should we include videos?
10. when selecting best on a photo in a group, it removes existing favorite
    state if it was already a favorite, regardless of selecting "favorite" or
    "not now".
11. it looks like the screen for a completed group is different to that of an
    un-reviewed group, why is that?
12. when looking at the favorite queue, i should be able to view the photo and
    remove it from the favorite queue (but still keeping it)
13. cannot see photos that are queued for favorites in the progress screen
14. should be able to open and view a photo from the progress screen instead
    of the current action that happens when clicking a photo and the only
    option is sending a photo to the edit queue. Instead the normal photo view
    screen should be used (from group/single review)
15. share queue?
16. organize queue: move to a different album. Compare button swaps with to
    edit, that way the top 3 bigger buttons are keep, compare, cull, and below
    that are the queue options: edit, favorite, organize, share
17. recent days, maybe it should be un-reviewed days or something? Or maybe 3
    most recent days and then the 2 most recent incomplete or un-reviewed
    days? When all recent days are done, but i need to work on other, older
    days, there is no indication that i need to
18. double tap a photo to reset zoom when zoomed in
19. "Keep rest" button can just say "Keep"
20. when all singles are reviewed, you cant go back into the single group like
    you can the other groups, it takes you straight to the cull list
21. show date along with the time
22. 2 photos in a group, 1 is not related, the other is then a lone photo in a
    group, technically a single, which it should also be
23. when all photos from a group get sent to singles, and then you go back to
    the session screen, you can still see the empty group there with no photos
24. Not in group folder 6: bad scenario where you want to compare photos from
    2 groups as if they are in one. Very important to get grouping right,
    similarity needs to be weighted higher, or we need a way to manually move
    photos to/between groups and merge groups, but thats complicated to code
    and makes more work for the user that we are trying to eliminate, so
    getting grouping right is very important! Can make the grouping tighter,
    but similarity becomes too strict. Need to have similarity still weighted
    higher than time, but just with a lower threshold to land in a group. Time
    should be a guide as to what can be in a group, but never the reverse:
    photos should never be excluded from a group because of time. I could take
    the same photo of the same thing, every day for a week, and they should
    still be grouped. Its always better to be over eager with groups, as
    photos can be easily sent to singles, but there is no way to send photos
    from singles to a group, and we don't want that extra manual work. We just
    want groups to work. Similarity should always come into play and never
    totally excluded, looser grouping means a lower similarity threshold.

## Samsung device verification (Tristan, 2026-07-23)

- **Trash + restore: working.** Culls land in Gallery trash and restore.
- **Favourites: working.** Batched favourite/unfavourite surfaces in Gallery.
- **Editor launch: still broken** — but the m0.6 diagnostics finally captured
  the real failure. Screenshots (2026-07-19, kept locally in `screenshots/`,
  not committed) show, for both attempted actions:

  ```
  Could not open the photo
  No installed app could edit or view this photo. Install a photo editor or
  gallery app and try again.

  Diagnostics
  URI: content://media/external/images/media/1000168830
  ACTION_EDIT: java.lang.SecurityException: UID 10434 does not have
  permission to content://media/external/images/media/1000168830 [user 0]
  ACTION_VIEW: java.lang.SecurityException: UID 10434 does not have
  permission to content://media/external/images/media/1000168830 [user 0]
  ```

  A later attempt toasted "Opened in viewer — use its edit button" (the
  in-app fallback). So handlers exist; the launch dies on a **URI permission
  grant** `SecurityException` at dispatch, and the dialog's "no installed
  app" copy misdiagnoses it. Root-cause fix is the top item in
  [Plan_20260723.md](Plan_20260723.md).
