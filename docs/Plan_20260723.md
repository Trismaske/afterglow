## m0.7 — "Feedback: trust the groups, work the queues"

### A. Editor launch — prove the grant model, then fix it  *(top priority; gate 0; R#1)*

The m0.6 diagnostics show both `ACTION_EDIT` and `ACTION_VIEW` dying with
`SecurityException: UID <ours> does not have permission to
content://media/external/images/media/<id>`. The review disproved the
original "chooser/Expo drops the grant flags" hypothesis: `lib/edit.ts`
already passes read+write flags, Expo's `IntentLauncherModule.kt` calls
`intent.addFlags(...)` on the dispatched intent, and the current path never
chooser-wraps. The stronger hypothesis is that **Afterglow holds broad read
access but neither owns nor holds write access to the MediaStore item**, so
asking Android to delegate read+write fails at dispatch. Android's documented
route to write access for other apps' media on 11+ is
[`MediaStore.createWriteRequest`](https://developer.android.com/training/data-storage/shared/media#update-other-apps-media).

**Gate 0 — diagnostic debug APK + Samsung matrix (before any fix commits):**

1. Record the package/UID actually named by the exception — do not assume it
   is Afterglow's.
2. In native code, log `checkUriPermission` for Afterglow's read and write
   modes on the target URI, and prove `ContentResolver.openInputStream(uri)`
   succeeds.
3. Try, in order: direct `ACTION_VIEW` read-only; direct `ACTION_EDIT`
   read-only; `ACTION_EDIT` read+write.
4. If write is the failing mode: test a `createWriteRequest` approval
   immediately before EDIT, instead of re-granting a permission Afterglow
   does not hold.
5. Only add `<queries>` intent filters and explicit per-package
   `grantUriPermission()` if the matrix proves they are needed — package
   visibility does not block dispatching an implicit intent.
6. Contract: **VIEW receives read-only**; a viewer's own later editor hop is
   outside Afterglow's result contract. No revoke-on-return starting policy;
   if per-package grants prove necessary, test editor save/return behavior
   before choosing any revocation point **(autonomous: revocation timing,
   only if reached)**.

**Gate 0 result (2026-07-23, matrix run via device automation):** the
matrix completed on the Samsung tester device (Android 16) and the API-36
emulator with **identical signatures**, so the failure is stock Android 16
behavior, not OEM-specific, and every regression stays emulator-testable:

- `VIEW` and `EDIT` both dispatch fine with a **read-only** grant (the
  chooser/editor opened on both targets, with zero handlers visible to
  `queryIntentActivities` — package visibility limits queries, not
  dispatch, as the review predicted);
- attaching `FLAG_GRANT_WRITE_URI_PERMISSION` reproduces the captured
  `SecurityException` **verbatim on both targets** — Afterglow holds broad
  read via `READ_MEDIA_IMAGES` but owns no write access it can delegate.
  m0.6 attached the write flag to *both* EDIT and VIEW, which is why both
  failed in the tester capture;
- after one `MediaStore.createWriteRequest` approval, the previously
  failing EDIT read+write intent dispatches and the editor opens;
- `checkUriPermission` reports read+write denied on both targets (media
  access is not URI-grant-based), `openInputStream` succeeds, and the
  exception's UID is Afterglow's own.

**Selected mechanism (implemented in gate 3):** the Edit action requests
`createWriteRequest` approval for the asset (auto-approved without a
dialog when already writable), then dispatches `ACTION_EDIT` with
read+write grants; if the user denies write access, fall back to EDIT
read-only (a save-as-copy lands in edit detection); the `ACTION_VIEW`
fallback stays read-only per this item's contract. No `<queries>` entries
and no per-package `grantUriPermission()` are needed.

**The fix** is whichever mechanism the matrix selects, implemented in
`modules/media-store-actions` (or a sibling native module), with
`lib/edit.ts` / `lib/editFallback.ts` routed through it. The pure fallback
chain (EDIT → VIEW → in-app viewer) is unchanged and keeps its tests. The
dialog copy must distinguish "permission denied" from "no handler installed"
— the current "install a photo editor" message misdiagnoses. Samsung is
retested at gate 0 (matrix) and again immediately after each native path in
gate 3 — not first at the release candidate (R#1).

### B. Grouping v2 — similarity-first within the session draw  *(#24; fixes #2, #22, #23; R#2, R#8)*

The tester's spec, taken as the requirement: similarity always participates
and outweighs time; **time never excludes**; over-eager grouping beats
under-grouping because photos are easily ejected to singles but never
promoted into groups.

**Bounded-session contract (R#2):** similarity components are complete only
within the selected draw — the loader stops at a boundary before hashes
exist, so no post-selection grouping can know about similar photos beyond
it. All copy honours this: the "don't split groups" cap extension re-targets
similarity components (still bounded at +200) but its setting text must not
promise that a *global* similarity group is unsplit — reword to "keeps the
groups in this session whole" **(autonomous: exact copy)**. The
global-component contract (full-scope enumeration/durable similarity index)
is explicitly deferred.

**Candidate window (N#6, P5#2)** — "the draw" and "its similarity
components" are staged explicitly so the cap and the grouping are not
circular, and carried staged culls can never starve unreviewed work:

1. page **unreviewed** photos in draw order up to `cap + 200` (base draw
   plus lookahead quota) or end of scope, within a stated hard
   MediaStore-page budget **(autonomous: page budget)** — the scan is
   driven by this quota; **retention never controls paging** (P7#1: a full
   reservoir must not stop the loop before `cap + 1` is even seen);
2. during the same paging, collect a **staged reservoir** bounded at 200
   staged culls nearest the paged range **(autonomous: reservoir bound)**
   — a long staged-only stretch beyond the page budget stays in the
   global cull list;
3. merge and evict to the retained ceiling (≤ `cap + 200` photos, ≤ the
   700 hard ceiling): with "keep groups whole" on, **unreviewed lookahead
   structurally outranks staged context** — each admitted lookahead photo
   evicts the staged row farthest from the drawn work first; with it off,
   lookahead is dropped and the window is the base draw plus reservoir
   **(autonomous: exact eviction order)**;
4. hash and group the complete retained window;
5. with "keep groups whole" on, select the **component closure of the
   base set (P8#2)**: the first `cap` unreviewed photos plus every
   retained unreviewed member of every component intersecting that base
   set — similarity components need not be contiguous in draw order, so
   extending only the cut photo's component can still split a selected
   component whose later member lies beyond the cap. Closure stays within
   the already-retained window (≤ 700); no recursive expansion beyond it
   — the bounded-session contract holds. With the toggle off, exactly the
   base draw plus carried context;
6. retained staged culls enter the final session when they fall within the
   selected set's chronological span or share a component with the
   **closed** selected set (P8#2) — the rest stay in the global cull
   queue **(autonomous: context-membership rule)**;
7. chronologically order the final selected set for presentation.

**Forward-progress invariant (P5#2):** if a scope contains any present
unreviewed photo, every newly prepared draw contains unreviewed work, and
repeated replacement can never return the same staged-only window forever.
A scope containing only staged culls draws them (there is no unreviewed
work to starve) and Home points at the cull list.

**Resumable page-budget exhaustion (P8#1):** MediaStore pages are
mixed-state (it knows nothing of SQLite review state), so exhausting a
work slice's page budget proves nothing about remaining unreviewed work —
it is a **continuation state, never a draw boundary**. The loader retains
the MediaStore continuation cursor plus the bounded candidate/reservoir
state and keeps scanning in bounded, cancellable slices (analysis progress
shown) until the **continuation target** is met (P9#1): with whole-groups
on, until `cap + 200` unreviewed candidates are collected or end of scope
is reached — stopping at the base cap could leave a similar `cap + 1`
partner sitting unloaded in the next slice, undoing component closure;
with whole-groups off, until the base `cap`, since lookahead would be
discarded. The slice budget controls yielding, progress, and cancellation
only — it is never a semantic candidate boundary. End of scope with fewer
than `cap` unreviewed photos produces the smaller valid draw; zero proves
the staged-only case **(autonomous: slice-chaining UX over returning a
smaller-than-cap session)**. No session is created — and no active session replaced — with
a staged-only candidate while unreviewed work remains unproven;
cancellation leaves the old session resumable and never promotes the
partial candidate. (If a native/SQLite anti-join that truly pages only
unreviewed assets is implemented instead, it must be proven for untracked
assets, canonical ids across volumes, limited access, and more bind
parameters than one SQL chunk.)

With whole-groups off, the hashed window is the base `cap` draw **plus any
carried staged context** (P6#5 — carried culls are displayed and re-grouped
in every mode, so they are always part of the stated hash count). Tests pin
oldest/newest draw order, a component crossing the cap, a component
reaching the 700 hard edge, multi-album early-stop completeness, **the
P7#1 boundary fixture — 200 staged rows already retained before the base
cap, the similar unreviewed pair at `cap`/`cap + 1`, asserting the exact
retained and selected ids, that one staged row is evicted for the
lookahead member, and that retention never exceeds 700 (P6#2, P7#1)**, a
maximum-page-budget case with a very long staged-only stretch after the
cut, **the P8#1 continuation fixture** (first unreviewed photo one page
beyond the budget: several continuation slices, cancellation/restart, both
draw orders, end-of-scope staged-only proof, and no staged-only
replacement committed while unreviewed work is unproven), **the P9#1
cross-slice fixture** (the base cap reached by a slice's final row and a
similar `cap + 1` row opening the next slice: whole-groups on resumes and
includes the partner through closure; off stops at the cap; cancellation
between slices creates or replaces no session; restart resumes without
promoting the base-only partial), **the P8#2
closure fixtures** (a non-cut selected component with a member after the
cap; two components extending beyond the cap; a staged member plus an
unreviewed lookahead member in one non-cut component; newest-first
non-contiguous members; closure reaching the 700 edge — asserting exact
session membership and that every represented component contains all its
retained unreviewed members), and the
P5#2 starvation fixtures: more-than-cap and more-than-700 staged prefixes
in both draw orders, mixed staged/unreviewed similarity components,
repeated replacement, and a staged-culls-only scope.

**Real maximum sizing (R#2):** settings allow 500 photos and the extension
adds 200, so a draw can reach **700 photos = 244,650 pairs**. Hamming
comparison stays trivial; the real budget is image decode/dHash generation.
The hash cache (`lib/similarityHashes.ts`) is reused across sessions;
analysis reports progress, is cancellable, and unmount/session-replacement
must stop it — progress can never update a replaced screen. Timing is
measured at the 700 ceiling on emulator and Samsung during gate 2.

Core (`packages/core`, new module or `similarity.ts` extension):

- New `groupBySimilarity(items, hashes, opts)`: pairwise 64-bit dHash
  Hamming distance over the whole draw, **connected components** where
  distance ≤ threshold. Time proximity *relaxes* the bar for borderline
  pairs by a bonus — it can only ever add, never exclude. The bonus applies
  within `MOMENTS_GAP_MS` and starts at +6 bits **(autonomous: gap choice
  and bonus size, tuned on device)**.
- **Null-hash rule (R#8):** a photo whose hash is missing or failed never
  joins a similarity component — it lands in singles **(autonomous)**.
- Components of size 1 are singles. Groups order chronologically by earliest
  member; members are chronological within the group.
- **Slider semantics:** the value is the base "fingerprint bits allowed to
  differ"; chips 12/16/20/26/32 (default 20) keep their positions. The old
  `64 = time-only` special value is **removed from the slider** (R#8: 63 vs
  64 would be discontinuous and contradicts "similarity always
  participates"). Legacy time-gap clustering survives as a separately named
  settings toggle, "Group by time only (legacy)", which uses `clusterByGap`
  verbatim and disables the slider while on; a stored 64 migrates to
  toggle-on + slider 20 (standing re-map policy) **(autonomous)**.
- `clusterByGap`/`refineClustersBySimilarity` remain exported (desktop story
  engine and the legacy toggle still use them).

**Anti-chain validation (R#8):** connected components chain A~B~C even when
A≁C, and removing time boundaries raises percolation risk. Add a small
checked-in **anonymized hash+timestamp fixture corpus** (built from the
tester's failure folders) pinning: expected group precision/recall; an
adversarial similarity chain that must not absorb unrelated endpoints;
repeated/common compositions (dark frames, screenshots, sky, documents);
missing/failed hashes; and maximum component size + runtime at the
700-photo ceiling. If unrestricted components over-group on the corpus,
gate 2 falls back to an edge-confidence rule or complete-linkage
representative checks before considering manual merge tooling.

  remaining photo joins singles (#22).
- A group emptied into singles disappears from the Groups screen (#23).
- The singles pseudo-group card is hidden when it holds 0 photos (#2).
- **Enforced in core, not only UI/SQLite (C#6):** the current model does
  the opposite — ejecting from a 2-photo group leaves a one-member group
  (an existing unit test expects it), and ejecting the last alive member
  can leave a completed group holding a culled survivor. `DeckSession`
  changes so eject dissolves the group (both photos become singles) with
  best/cursor state repaired and assignment persistence in the same
  captured transaction; `DeckSession.create()` canonicalizes or rejects
  singleton input groups. These core regression tests are **entry criteria
  for gate 2**.

### C. Groups become durable — membership keyed by run, not by day  *(#8; R#3)*

Group membership persists to SQLite with **one membership truth** and no
day-keying (a similarity group may span days). Schema **v8** — migration in
`db/database.ts` (schema lives there; store operations live in `db/store.ts`
— R minor), atomic migration runner with fresh, v7-upgrade,
interrupted-write, and replacement-session tests:

- `grouping_runs(id, session_id, created_at, scope, provenance)` — one run
  per real session, enforced by a **partial unique index** on non-null
  `session_id` (N#1); the v7-migration legacy run has `session_id NULL`
  and `provenance = 'v7-migration'`, since v7 has no reliable
  photo-to-session relation (C#3).
- `photo_groups(id, run_id, best_photo_id NULL)` — the group id is
  **synthetic and stable**; identity never depends on the earliest member.
  `best_photo_id` makes best-of-group durable (also closes the R#4 loss);
  invariant: it is NULL or a current member of that group — enforced by the
  atomic store operations and pinned by tests.
- `photo_group_assignments(photo_id PRIMARY KEY, run_id, group_id NULL)` —
  **every drawn photo has exactly one current assignment**, enforced by the
  primary key; `group_id NULL` is a **durable single** (N#1). Never-drawn
  photos have no row, so durable singles and untracked rows stay distinct.
  Foreign keys to runs and groups; "taken day" stays a property of the
  photo, never of the group; a dissolved group's row is deleted only after
  its assignments are re-pointed, in one transaction.
- `photos.group_id` is **deprecated**: v8 migrates existing assignments into
  the relation as one legacy run, after which the column is neither read nor
  written (retained to avoid a SQLite table rebuild) **(autonomous)**.

**Executable integrity (C#3)** — declared constraints must actually run:

- `PRAGMA foreign_keys = ON` on every opened connection (the current init
  enables WAL but never FK enforcement), asserted in tests; migration tests
  run `PRAGMA foreign_key_check`.
- The redundant keys are made provable with composite constraints:
  assignments carry `(run_id, group_id)` as a composite FK onto
  `photo_groups(run_id, id)` so the group provably belongs to the
  assignment's run; `photo_groups.best_photo_id` is a composite FK onto
  `photo_group_assignments(group_id, photo_id)` so the best is provably an
  assigned member; assignment `photo_id` FKs onto `photos.asset_id`.
  `ON DELETE` behavior is stated per relation; store-level checks remain a
  second line of defense, not the meaning of the declared constraints
  **(autonomous: composite FKs vs deferred FKs vs triggers)**.
- The one-active-session invariant is enforced with a partial unique index
  on `sessions`, not call-site discipline (C#3).

**Canonical volume-qualified media identity (P4#2):** the legacy Expo
`asset.id` is the raw MediaStore `_ID`, which is ambiguous across storage
volumes — yet `photos.asset_id` and every session/group/queue relation ride
on it, and the current editable-URI fallback even constructs a synthetic
`content://media/external/…` URI. v8 makes identity volume-qualified end to
end:

- the canonical key is a stable value derived from the **specific content
  URI**, stored alongside `volume_name`, the raw `_ID`, and the current
  specific URI;
- core session items, `photos`, group assignments, hashes, and every queue
  use that key; every native action (edit, trash, favourite, organize,
  share) consumes the **stored specific URI**, never a re-resolved bare id;
- the migration maps existing raw ids conservatively via the stored file
  URI plus a native lookup — an ambiguous or inaccessible legacy row
  becomes `unknown`, is never attached to whichever same-id row a merged
  query returns, and is never eligible for a destructive request; and
- the C#2 tests extend with two fixtures sharing the same raw `_ID` on
  primary and SD storage: independent SQLite rows, correct presence
  results, primary-only organize rejection, and correct native URI routing
  for every action type.

**Crash-safe, transitive identity migration (P5#1):** a v7 raw id lives in
more places than `photos.asset_id` — every `sessions.snapshot` JSON (item
ids, state-map keys, member/alive/single ids, best ids, compare history),
`duels.winner_id` / `duels.loser_id`, and `photo_hashes.asset_id`; legacy
group ids that embed a photo id stay opaque legacy identifiers and are
never parsed as canonical photo ids. Static `MIGRATIONS` SQL cannot perform
the native lookup, and holding one transaction open across a library scan
is fragile — so the migration is a two-phase protocol:

1. read the v7 rows and parseable snapshots before any mutation;
2. resolve a complete **occurrence-scoped** identity map (P6#1) through
   one volume-aware native adapter, bracketed by the P4#3
   volume/generation fence; the map is retryable migration input only —
   `user_version` does not advance;
3. in one exclusive SQLite transaction: rewrite `photos`, `duels`, every
   restorable snapshot, and mappable hash rows; apply P4#4's assignment,
   cull, and active-session normalization; create the v8 relations; run
   the integrity checks; then advance `user_version`;
4. unresolved rows get deterministic `legacy-unknown` identities with an
   explicit `identity_status` — viewable/re-decidable where possible but
   never eligible for Edit, Trash, Favourite, Organize, or Share until
   re-resolved; and
5. an orphan `photo_hashes` row is **discarded, never guessed** (v7
   computes hashes before `createSession()` inserts photo rows, so a hash
   can have no photo row or URI to resolve a volume from); an active
   snapshot that cannot be rewritten safely is repaired from its
   structurally readable state map, else conservatively abandoned under
   item H's ownership rules **(autonomous: repair-vs-abandon boundary)**.

**Deterministic ordering (P5#1):** among anomalous multiple unfinished v7
sessions, the **newest valid snapshot** survives; when one photo occurs in
several historical sessions, the newest valid snapshot containing it
supplies current membership.

**Fresh-install ingestion boundary (P5#1):** every
`pagePhotosInRange()` / candidate / day loader receives or derives the
specific volume and content URI before constructing a core `MediaItem` —
the legacy Expo asset's raw id + `file://` URI never reach the model.

Migration tests run against a **fake native identity map** with fixtures:
an active snapshot containing groups, singles, best, culls, and compare
history; completed snapshots and `duels` rows; one mappable and one orphan
hash; the same raw `_ID` on primary and SD storage; one
unknown/inaccessible legacy row; a crash before mapping, after mapping but
before the transaction, and in each transaction phase; and reopen/resume
proving no raw id remains in any live v8 relation or snapshot.

**Occurrence-scoped resolution (P6#1):** one global `raw id → key` map is
still ambiguous — v7's `photos.asset_id PRIMARY KEY` holds one current row
while two historical snapshots can describe *different* assets that shared
raw id `42` on different volumes, so a bare-id mapping would rewrite one
snapshot and its duel rows to the wrong photo. Migration records are keyed
`(owner kind, owner id, raw id, stored URI)`:

- a `photos` row resolves from `(raw id, stored file URI)`;
- each snapshot item resolves from `(raw id, that item's file URI)`, and
  the snapshot's state-map/member/best/history references use its
  item-local mapping;
- a duel resolves through its `session_id` and that session's rewritten
  snapshot; and
- a hash row is retained only with one unambiguous owning occurrence —
  otherwise it is discarded as cache.

Fixture: two historical sessions plus duel rows sharing one raw id on
different volumes — both snapshots must resolve to their own assets.

**Materialized occurrence parents (P7#2):** v7 holds one `photos` row per
raw id, but two historical snapshots can resolve that raw id to two
different canonical assets — rewriting the second snapshot is not enough
when its canonical id has no `photos` parent: no FK target for group
assignments, no current-state row for browse/History, and a re-decide
`UPDATE photos … WHERE asset_id = ?` that silently affects zero rows. The
migration builds the canonical `photos` relation from **resolved
occurrences**, not only by rekeying existing rows:

1. the occurrence matching the legacy row's stored URI inherits that
   row's relational state, queue intents, timestamps, and hashes;
2. a distinct snapshot occurrence without a matching legacy row gets a
   canonical parent **synthesized** from its item-local URI, timestamp,
   kind, and state map (the `DeckSessionJSON` shape already carries
   them) — `day` is derived, presence comes only from the fenced native
   result, and unsupported queue/history fields stay empty;
3. several occurrences resolving to one canonical asset collapse to one
   row under the newest-valid-snapshot current-state rule — never
   duplicates;
4. a distinct unresolved occurrence gets its own deterministic
   `legacy-unknown` parent and never borrows the raw-id row's destructive
   intent; and
5. duels, restorable snapshots, assignments, and best references are
   inserted or rewritten only after those parents exist.

The same-raw-id/two-volume fixture asserts **two `photos` rows**, not just
two rewritten snapshots: reopen both completed sessions, browse and
re-decide each asset, run `foreign_key_check`, and prove a staged state
belonging to one URI never transfers to the other. The inverse fixture —
one physical asset appearing in several snapshots — produces exactly one
row under the newest-valid-snapshot rule.

**Quarantine has a return path (P6#1):** a row can be `legacy-unknown`
merely because migration ran under limited access or an unmounted SD
volume — when access returns, fresh ingestion would otherwise insert a
duplicate canonical row for the same physical photo. An atomic
`resolveLegacyIdentity` transition:

- matches only on strong evidence (stored URI/volume + raw id, or a
  content hash where available);
- rekeys every live FK, queue, group assignment, duel, and active
  snapshot, serialized through the item-D live-session command queue
  (P6#3);
- merges with an already-inserted canonical row under a pinned conflict
  rule — review history and staged state on the quarantined row win over
  a freshly ingested unreviewed row; with history on both sides the newer
  `activity_at` wins **(autonomous: conflict rule)**;
- keeps destructive ineligibility until the match is verified; and
- resets History pagination and source caches after the rekey.

Tests: permission-limited migration → later full access, unmounted SD →
remount, a canonical duplicate already inserted, an unknown staged cull,
and process death during the rekey.

**Merge matrix (P7#3):** the current-state winner alone does not merge the
rest of the model — a primary-key rekey can collide with
`photo_group_assignments.photo_id`, `share_queue.photo_id`, and every
one-current-intent constraint — so `resolveLegacyIdentity` resolves each
relation explicitly:

- **identity/presence:** the canonical URI/volume/raw id and the
  authoritative current presence result win;
- **current review state:** the adopted rule; staged destructive state is
  never inferred from the fresh duplicate;
- **queue intents:** chosen independently per queue by intent timestamps,
  with C#7 cleanup/presence eligibility re-run after the merge;
- **metrics:** first-event timestamps keep the earliest non-null
  occurrence; `activity_at` reflects the winning/latest activity;
- **grouping:** the newest-run assignment rule decides; the losing group
  is dissolved/repaired and any invalid best cleared;
- **events:** duel/share/trash events union by their stable ids — never
  turned into current-state winners, never double-counting reclaimed
  bytes;
- **active snapshot:** both aliases are replaced with the canonical id in
  one P6#3 command, an impossible duplicate item is rejected, and
  cursor/undo state is preserved; and
- **caches/baselines:** only entries proven to describe the canonical
  current asset survive.

**Strong evidence means cryptographic (P7#3):** the SHA-256
`photos.content_hash` may support an identity match; the perceptual
`photo_hashes` dHash deliberately collides for similar photos and never
authorizes an identity merge or any destructive action.

Merge tests: conflicting group assignments, a best marker, opposite
favourite and organize intents, current-cycle share membership, both
metric histories, an active snapshot containing one alias, and an
already-accounted trash event — with failure injected after each merge
phase, reopened, and proven idempotent.

**Non-live legacy blobs (P6#1):** an un-restorable historical snapshot is
archived during migration as a sanitized, non-live legacy blob that no v8
path reads — the "no raw id survives" guarantee applies to live relations
and restorable snapshots.

**Deterministic v7 normalization (P4#4):** "migrate existing assignments
into one legacy run" must be an explicit classification, not a copy:

- valid persisted snapshots provide the evidence for drawn membership;
  `group_id IS NULL` is ambiguous (a drawn single vs a never-drawn tracked
  row such as a detected edited copy), so ambiguous null-group rows stay
  **unassigned** — durable singles are never invented;
- legacy groups with fewer than two proven members canonicalize to singles
  (v7's `makeSingle()` cleared only the ejected photo's `group_id`, so
  one-member legacy groups are reachable);
- unowned legacy `culled` rows reset to `unreviewed` (item H's orphan
  cleanup), and an anomalous v7 database with multiple unfinished sessions
  is normalized before the one-active-session partial index is created;
- the composite-FK parents are declared explicitly — UNIQUE on
  `photo_groups(run_id, id)` and
  `photo_group_assignments(group_id, photo_id)` — and the cyclic
  best/member relation pins its ordering: create the group with no best,
  insert assignments, then set best; clear best before moving or deleting
  its assignment (tested); and
- v7 fixtures: a detected copy, a two-member group after `makeSingle`, an
  orphaned abandoned-session cull, a valid active staged cull, and
  duplicate unfinished sessions — reopened after migration asserting the
  ≥ 2 invariant, one active session, assignment provenance, and
  `foreign_key_check`.

Semantics:

- Membership becomes durable **at session creation** (safer than
  bank/complete — R#3).
- `make single`, group dissolution, best-of-group, and staged decisions
  update the relation **in the same transaction** as the session-snapshot
  write, so snapshot and SQLite cannot disagree.
- Re-grouping in a later session replaces assignments **only for the assets
  actually drawn** into that session, then **repairs intersected leftovers**
  (N#1): an old group left with fewer than 2 members dissolves — the
  survivor becomes a durable single and the group row is deleted; a group
  that loses its best member has the marker cleared. Groups wholly outside
  the draw (e.g. capped out) survive untouched **(autonomous)**.
- Assignment tests (N#1): grouped → regrouped, grouped → single, partial
  old-group dissolution, best-member removal, and one photo drawn in three
  successive runs.
- **Cross-day groups:** a group is listed on every day that owns ≥ 1 member;
  opening it always opens the **complete group**, with out-of-day members
  shown and dated (date+time headers, item D). DayProgress never clips a
  group to its day **(autonomous)**. Count contribution is pinned in item J.

Reopening a completed (or partly reviewed) day renders its groups and
singles pseudo-group in the same deck browse/re-decide mode as a live
session; photos never drawn into any session still show in the flat grid.

### D. One deck, one photo viewer — with a mutation boundary  *(#5, #6, #11, #14, #18, #19, #20, #21; R#9)*

- **Culled photos stay visible** in the deck with their ✕ badge — no more
  disappearing on cull; the deck just advances past them. Culls still
  execute only at the cull-list confirmation (#6). **This is a core model
  change, not screen polish (R#9):** `DeckSession`'s cursor currently
  follows alive members; keeping culled members visible changes cursor
  semantics and the serialized snapshot. Core ships the model +
  serialization migration with tests before any screen work. The migration
  also fixes a **reproduced release-blocking defect (C#5)**: `cullKept()`
  currently leaves a re-decided keeper in `aliveIds` (and as `bestId`),
  producing a snapshot `DeckSession.fromJSON()` rejects — today a process
  restart after re-deciding a completed keeper as Cull abandons the active
  session as corrupt. Round-trip regression tests: keep group → cull kept →
  serialize/reopen; the same path when the photo is best; cull → keep →
  clear decision; and a restart after **every** re-decision transition.
- **Singles auto-advance**: after any decision in the singles deck, move to
  the next undecided photo (#5).
- **Completed = unreviewed, one layout** (#11): a completed group opens in
  exactly the same deck screen as an unreviewed one — badges shown, all
  re-decide actions live; the only difference is completing it again doesn't
  auto-advance.
- **Singles re-entry parity** (#20): a fully reviewed singles pseudo-group
  reopens from the Groups screen like any completed group.
- **"Keep rest" → "Keep"** (#19): the big Keep button acts on the *current
  photo* and advances; "Keep remaining N" moves to the deck footer as the
  explicit group-finisher **(autonomous: placement)**.
- **Double-tap resets zoom** when zoomed, in the deck overlay and Compare
  (#18).
- **Date + time together** wherever a timestamp shows: deck header, queues,
  progress, history (#21). One shared formatter in `lib/format.ts`.
- **One standard photo viewer** (#14): a single full-screen photo view —
  zoom, date+time, decision badges, decision/queue buttons — shared by deck
  browse, Progress/DayProgress, History and the queue screens, replacing the
  progress screens' send-to-edit-only sheet.
- **Mutation boundary (R#9):** one visual component, two mutation routes —
  active-session assets go through `SessionContext.redecide` / queue
  persistence (never direct DB writes, which would desynchronize the
  persisted `DeckSession` snapshot); out-of-session assets use explicit
  store transitions. Per-state action matrix **(autonomous)**: untracked
  photos get view/zoom + queue actions but no review decisions; photos with
  a missing/trashed asset render a placeholder with all actions disabled.
  Organize stays available on already-organized photos — organizing is
  repeatable (N#8, item E). Tests prove no viewer
  action can leave the snapshot and SQLite disagreeing.
- **Compound Compare verdicts are one command (C#11):** "X is better"
  currently awaits `markBest()` and then separately calls
  `recordCompare()` / `compareCull()`, each persisting its own snapshot —
  process death can leave a durable star without the compare record or
  loser decision the button promised. Each compound verdict becomes one
  SessionContext command that mutates core once and writes the snapshot,
  compare row, best assignment, and optional cull together.
- **Deck validation (C#13, P5#5):** `setCursor()` and snapshot validation
  require a finite **integer** via `Number.isInteger()` — today `1.5` is
  silently floored and `NaN` survives the clamp math; `fromJSON()` verifies
  `group.complete` against remaining unreviewed members; fresh
  `DeckSession.create()` rejects media/group shapes the restore path would
  reject or that violate the ≥ 2 invariant. Property-style transition →
  JSON round-trip tests complement — never replace — explicit
  invalid-input tests.
- **Presence transitions reach the active snapshot (P5#3):** full-scan and
  History fast-path presence changes route through the same mutation
  boundary as user decisions, in one transaction that updates
  `is_present`, queue cleanup, group/best projection, **and the active
  snapshot** together. The core model serializes per-photo availability
  with tested unavailable/available transitions that remove/reinsert
  photos from live cursors and completion without erasing durable group
  provenance **(autonomous: availability transitions chosen over full
  snapshot rebuild)**; restoration reinserts the photo with the reconciled
  DB state (`unreviewed`), never the stale snapshot verdict. Tests pin
  disappearance/restoration while facing an unreviewed member, a best
  member, a staged cull, a two-member group projecting to one present
  member, and a photo already `trashed` — each repeated across process
  restart.
- **One live-session command queue (P6#3):** `SessionContext` holds a
  mutable in-memory model whose decisions persist through a FIFO queue —
  a background writer touching `sessions.snapshot` directly can be
  overwritten by a pending decision write, or overwritten back by the
  stale in-memory model. Every mutation touching an active session —
  scan/History reconciliation, global-cull confirmation, organize repair,
  legacy-identity rekey — enters one SessionContext / session-repository
  command queue: wait for prior persistence, mutate the in-memory
  `DeckSession`, commit snapshot + relational changes once, then advance
  the committed baseline. Store-only callers may mutate out-of-session
  photos but must detect active membership and delegate; a snapshot
  revision/CAS check makes a stale writer fail rather than silently win.
  Tests race a delayed decision write against disappearance, restoration,
  global trash confirmation, and organize repair — the live UI and the
  reopened snapshot must both contain both mutations, in either arrival
  order.

### E. Deck relayout + the queue family  *(#3, #12, #13, #15, #16; R#6, R#7)*

- **Button relayout** (#16): the big three become **Keep / Compare / Cull**;

**Organize queue** (#16) — "move to a different album" (R#6):

- Target identity is **`(volume, relative path)`**, not an Expo album id.
  m0.7 moves stay on **primary external storage**: the picker hides
  non-primary-volume albums, and a source item on another volume is
  rejected with a clear message — never silently copied+trashed
  **(autonomous)**.
- **Volume-aware catalog boundary (C#2)**: today `sourceCatalog.ts` keys
  entries by lower-cased relative path and `sources.ts` strips the volume
  prefix, so volume identity is erased before any picker runs — the
  existing catalog *cannot* implement the boundary above. Gate 1/3 adds a
  small native MediaStore query exposing at least `volume_name,
  relative_path, bucket_id, display_name, photo_count`; source selection
  (intentionally cross-volume) stays separate from organize target
  identity. Pinned tests: the same `DCIM/Camera` path on primary and SD
  storage, primary-only destination filtering, SD-source rejection before
  any write request, source-fingerprint stability, and migration/fallback
  for the existing path-only `photo_sources` setting.
- Allowed destinations are validated paths under the top-level image
  directories (`DCIM/`, `Pictures/`) **(autonomous)**. "Create new album"
  is implemented as choosing a validated new destination path — the first
  moved batch creates it; no empty-album pre-creation (Expo album creation
  is asset-backed on Android).
- Durable SQLite intents (`none / queued / applied / error` with timestamps,
  the favourites pattern); the chosen target is stored durably and survives
  `error`, cancellation, and retry. While queued, remove-from-queue and
  change-target are both available.
- Batch apply in `modules/media-store-actions` via
  `MediaStore.createWriteRequest` + `RELATIVE_PATH` update — one system
  confirm, per-item verification after apply, idempotent and resumable.
  **Partial verification failure**: verified items become `applied`, failed
  items become `error` with retry; the batch never lies about the whole.
- **Post-move repair (R#6, N#8)** — one **SQLite** transaction executed
  after the external MediaStore move verifies (MediaStore and SQLite cannot
  share an atomic transaction): mark `applied`, refresh `photos.uri`,
  re-evaluate source-folder membership (DB filters use `photos.uri LIKE …`),
  invalidate the album catalog, evict stale thumbnails, and refresh the
  edit-detection URI, modification baseline, and hash caches (item L /
  C#9) so a move is never mistaken for an edit. Progress/history filters
  must be correct immediately after a move. A retry first recognizes
  "already at target" and completes the DB repair without prompting for
  another move.
- **Organize is repeatable (N#8)**: `applied` is not terminal — a photo may
  be moved to the wrong album or need another move later. Queueing a new
  target starts a new intent; the last applied target/timestamp is retained
  for History.
- New OrganizeQueue screen mirroring the favourite queue.

**Share queue** (#15) — multi-pass sharing (Tristan, 2026-07-23; R#7):

Android reports only that a sharesheet was opened — never the recipient or
delivery. So the model is honest by construction: **the queue is a
persistent working set, and each share is a recorded *pass* over a chosen
subset.** The queue does not clear on share; the user runs as many passes as
needed (15 photos to one person, an overlapping 10 to another, all 20 to a
third), then clears explicitly.

*Screen UX:*

- Thumbnail grid of queued photos (chronological). With nothing selected the
  primary button reads **"Share all N"** — the single-recipient case stays
  one tap. Tapping a thumbnail enters selection mode (gallery convention);
  the button becomes **"Share K selected"**; header gains **Select all /
  none** and a **Select unshared** chip.
- Each thumbnail carries a **✓ pass-count badge** (✓, ✓2, …) counting the
  share passes it joined during the current queue cycle — this makes
  overlapping subsets self-navigating ("which ones haven't I sent to
  anyone?" = Select unshared).
- Sharing fires `ACTION_SEND` for one selected photo and
  `ACTION_SEND_MULTIPLE` for two or more (N#5: receivers implementing only
  the single-image contract stay available), with the content URIs in
  `EXTRA_STREAM` and a read grant on **every** URI (item-A grant
  discipline applies).
- After the sheet closes: queue kept, badges incremented, snackbar "Sheet
  opened for K photos — queue kept for more sharing", and an **optional,
  fully skippable** "Label this share?" prompt (free text + recent-label
  chips, e.g. "Mum") — the only honest way to record *who*
  **(autonomous: prompt shape)**.
- **Clear queue** is explicit; if photos with zero passes remain, the
  confirm says "K of N photos were never shared. Clear anyway?". Clearing
  removes queue rows but **keeps share events for History** (R#7).
  Remove-one is available in selection mode and in the standard viewer.

*State model (R#7, N#5)* — there is deliberately **no** state claiming
delivery success, and History copy says "share sheet opened", not "shared".
Cycle and attempt identity are explicit ids, never timestamp comparisons:

- **Queue cycles (N#5)**: a monotonic `cycle_id` is minted when the queue
  goes from empty to non-empty; clearing the queue ends the cycle. A photo
  requeued later joins the new cycle.
- `share_queue(photo_id, cycle_id, queued_at)` — dedup by primary key on
  `photo_id`; re-queueing toasts "already in share queue". Persists across
  restart.
- `share_batches(id, cycle_id, attempted_at, opened_at NULL, label NULL,
  state)` with `state ∈ {launching, sheet_opened, error}`.
- `share_batch_members(batch_id, photo_id)`.
- **Crash boundary — at-most-once accounting (N#5, C#10)**: Android
  activity dispatch and a SQLite commit can never be one atomic operation,
  so the contract is explicitly conservative. Insert `launching` before
  dispatch; the native module reports **successful dispatch** separately
  from activity return, and the row is promoted to `sheet_opened` +
  `opened_at` immediately after; a `launching` row found at next app start
  reconciles to `error` — no badge, no History event, sharable again. A
  pass lost in the crash window is deliberately undercounted: the app
  prefers a possibly missing pass over a false "sheet opened" claim.
  Injected tests: pre-dispatch failure, post-dispatch/pre-promotion death,
  normal return, retry.
- A thumbnail's ✓ pass count = same-cycle batches with
  `state = 'sheet_opened'` that include the photo. Failed launches
  (`error`, `opened_at NULL`) never earn a badge and never appear as
  History events; retry is simply sharing again.
- Missing media: queue load drops photos whose MediaStore asset is gone,
  with a one-line notice (feeds the item-G reconciliation contract).
- **Batch-size policy (R#7)**: soft warning above ~50 selected ("Some apps
  can't receive this many at once"), no hard block **(autonomous:

**One cross-queue transition contract (C#7)** — trash, presence, and every

- select at most a conservative app cap of **500 URIs per OS request**

- each OS confirmation plus its verified SQLite write is **one logical

- resume after process death verifies external state before any retry; and
- honest multi-batch copy whenever a queue exceeds one system dialog

### H. Session replacement — atomic, carries staged culls, silent  *(#1; R#4, N#2; A1, P4#1)*

**Policy (Tristan, 2026-07-23, assumptions review, A1):** the old "a delete
list must be re-earned in a live session" rule is **overturned** — staged
culls survive session replacement alongside kept/edit decisions. Nothing is
ever lost, so replacement runs **with no dialog at all** (#1); the "discards
N staged culls" copy is removed, and the m0.2 interim-reset rule and Home's
"already handled" accounting update to match.

**Durable global cull queue (P4#1):** `photos.state = 'culled'` remains the
membership truth, but CullList and `confirmCulls()` now query that durable
truth directly, independent of the active snapshot — today both read the
active `DeckSession`, which is exactly why an out-of-draw staged cull was
unconfirmable. Re-deciding or confirming a durable cull updates any active
snapshot containing the photo, plus group/best state, `is_present`, and
queue state, through the item-D mutation boundary (confirmation additionally
runs the C#7 transition contract). Confirming a queue larger than one
MediaStore consent request applies in bounded native batches with honest
multi-batch copy (P5#4, item E) — the single-dialog promise holds per
batch, not for an arbitrarily large queue.

**Durable trash attempts + reclaimed-bytes attribution (P6#4, P7#4):**
confirmation no longer has an owning session — it can run from Home with
none active, and one bounded batch can span culls staged in several
abandoned sessions. A completed-outcome table alone also cannot survive
the dangerous window (sizes measured → Android trashes → process dies
before SQLite records anything), so the lifecycle is durable **before**
native dispatch:

- `photos.trash_generation INTEGER NOT NULL DEFAULT 0` (P8#4);
  `trash_batches(id, state, launched_from_session_id NULL, created_at,
  dispatched_at NULL, verified_at NULL)` with
  `state ∈ {preparing, launching, verified, verified_partial, cancelled,
  error}` — display state is **derived from member outcomes** (one
  undifferentiated `verified` cannot describe mixed results; member
  outcomes stay the accounting truth) **(autonomous: derived-state
  shape)**; `trash_reservations(photo_id PRIMARY KEY, batch_id,
  trash_generation)` — `photo_id` as primary key makes "one live attempt
  per photo" a schema invariant (a partial index on members cannot join
  the parent batch's `state`), with `batch_id` an ordinary indexed FK, not
  unique; and `trash_batch_members(batch_id, photo_id, trash_generation,
  measured_bytes, outcome)` with `PRIMARY KEY (batch_id, photo_id)` and
  `outcome ∈ {pending, trashed, absent_after_interrupted_launch,
  still_present, unknown}`;
- before dispatch, one P6#3 command-queue transaction creates the batch,
  records member ids + measured sizes, and **reserves** the culled rows —
  `preparing` inserts one `trash_reservations` row per member, capturing
  each photo's current `trash_generation` atomically (P8#4). One live
  attempt per photo; a reserved photo cannot be re-decided or selected by
  another batch. No SQLite transaction stays open while the Android
  consent UI is showing;
- dispatch/result handling re-enters the command queue: verify the
  specific URIs tri-state, commit verified members + queue cleanup +
  active snapshot once, and release cancelled/`still_present` members back
  to the cull queue. An interrupted `launching` attempt recovers at
  startup from its durable members and pre-measured bytes — **but
  ambiguous absence earns no credit (P8#3)**: the stored state cannot
  prove which side of dispatch the crash hit, and the asset may even have
  been deleted externally after a pre-dispatch crash. A recovered
  `launching` row whose URI is authoritatively absent repairs the photo to
  absent/trashed and cleans live queues while recording the **uncredited**
  outcome `absent_after_interrupted_launch`; `present` releases the
  reservation back to `culled`; `unknown` stays retryable and never claims
  reclaimed storage. History/UI copy never claims Afterglow moved an
  uncredited row to trash — the same conservative side of the non-atomic
  Android/SQLite boundary as C#10;
- `launched_from_session_id` is nullable and means the confirmation was
  launched **as an action of that session** — a Home confirmation stays
  unattributed even while some session happens to be active. A session
  Summary reports the verified bytes of confirmations launched from it
  **(autonomous: Summary attribution meaning)**;
- lifetime and Summary totals derive from **verified member rows**; if a
  cached `trash_batches.reclaimed_bytes` is kept, it is
  constrained/tested against the member sum — never a second accounting
  truth;
- the v7 `sessions.reclaimed_bytes` aggregate migrates under one explicit
  provenance key, so a failed/retried migration can never insert it
  twice; and
- **restore → re-trash counts again (P7#4, P8#4):** idempotency is per
  `(photo, trash_generation)`, with pinned transitions:
  cancelled/error/`still_present` terminals remove the reservation
  without incrementing the generation; a credited — or conservatively
  uncredited (P8#3) — authoritative absence consumes the reservation and
  completes that generation; authoritative Gallery restore increments
  `photos.trash_generation` exactly once before the photo can be staged
  again; the next attempt captures the new generation and may
  legitimately count a verified re-trash. A partial unique index over
  absence-terminal outcomes on `(photo_id, trash_generation)` prevents a
  second terminal outcome for one generation while still letting
  cancelled/error attempts retry; `resolveLegacyIdentity` merges
  generation/reservation/member rows under the P7#3 matrix without losing
  an in-flight reservation or combining two physical generations
  **(autonomous: generation-based accounting over
  one-lifetime-contribution)**.

Tests: death before dispatch, after dispatch but before result, and after
result but before DB promotion; cancellation; permission-denied/`unknown`

with an unrelated active session; an attributed session launch; retry;
restore → re-trash; a 500-item batch spanning old/current/out-of-session
culls; the lifetime total after v7 migration; death injected immediately

**Carried culls re-enter draws (Tristan, 2026-07-23):** a staged cull inside
a new session's range is drawn **as bounded context** — it surfaces with
its ✕ badge, re-forms its groups whole, and is re-decidable in place ("the
user can see their old decision when the photo comes up again" — A1) — but
it never consumes a base-cap slot: the base cap counts unreviewed work, and
carried culls ride within the `+200` allowance under item B's
forward-progress invariant (P5#2), so staged culls can never starve
unreviewed photos out of a draw. Staged culls outside the range or window
never become snapshot members; they simply remain in the durable queue.
Home/progress accounting counts a staged cull as reviewed / pending
confirmation, never as remaining work (item J).

Best-of-group is currently **snapshot-only** (N#2) — it survives process
restart while the session is active but is lost when the snapshot is
abandoned (fixed by item C's durable `best_photo_id`).

**Atomic replacement (N#2)** — replacement itself, not just cleanup, is one
operation. The candidate session is **prepared first**: the loader pages and
hashes the new draw, excluding banked kept/to-edit ids and *including*
in-range staged culls as pre-decided members. Then a single exclusive
SQLite transaction in `db/store.ts`, used identically from Home and
DayProgress, performs:

1. bank keepers (kept/edit decisions, as today);
2. mark the old session abandoned — staged culls stay `culled`; nothing
   resets; and
3. insert the new session with its grouping run, groups, and assignments
   (item C — membership is durable from creation), drawn staged culls
   entering as culled members.

A failure anywhere rolls the whole replacement back: the old session remains
active and resumable, and the new one simply does not exist.

**v7 orphan cleanup (P4#1):** shipped releases can already hold orphaned
`culled` rows from older abandoned sessions; exposing them wholesale as a
new global delete queue would resurrect stale destructive intent. The v8
migration keeps as staged only culls proven to belong to the current active
snapshot and conservatively resets unowned legacy culls to `unreviewed`
(item C's normalization). The carry policy applies without ambiguity after
that one-time cleanup.

Replacement tests (P4#1): a staged cull inside the new range, outside the
range, beyond the cap, after restart, after confirmation, after
re-decision, failure at each atomic phase, and the v7 orphan-cleanup case.

### I. Home — recent days that point at the work  *(#17; R#10)*

SQLite only knows previously-drawn photos, so older untracked days must be
discovered. **Chosen strategy (R#10)**: a cached **day index** in SQLite
**(autonomous)**:

- **Scan-keyed index (N#4, P5#5)**: `day_index_scans(id,
  source_fingerprint, volume_set, volume_generations_start,
  volume_generations_end, coverage, status, started_at, completed_at)`
  with `status ∈ {in_progress, complete, failed}` and
  `coverage ∈ {full, limited}` — the fence endpoints and coverage are part
  of the declared shape so gate 1 has one schema contract — and
  `day_index(scan_id, day, photo_count)`. The UI reads **only the latest
  `complete` scan**; a finished scan is promoted transactionally. The
  fingerprint covers the selected source roots and volume set — a source
  change never reuses incompatible rows; per-volume MediaStore
  generation/version values invalidate.
- The scan is **paged** (sorted by taken-date), deduplicates multi-album
  results, respects selected source roots, and picks up restored/moved
  assets. Scan work is cancellable and can never update a replaced screen;
  a cancelled or interrupted scan leaves the previous complete scan in
  force.
- **The completed scan is the authoritative presence reconciliation for
  item G** (N#3) — one full-library synchronization mechanism, not two.
  Per C#1 the **presence pass enumerates the full library** (every expected
  volume, completion judged per volume) even while day *counts* stay
  filtered to the selected source roots; under limited photo access the
  scan still counts what it can see but never authorizes negative
  reconciliation.
- **Mutation fence (P4#3):** a paged enumeration is not a stable snapshot —
  a photo can be inserted, deleted, restored, or moved between page
  requests. Per expected volume the scan captures the mounted-volume set
  and MediaStore version/generation **before** paging, enumerates, then
  reads them **again after**; negative reconciliation and scan promotion
  are authorized only when the volume set and both endpoints agree. Any
  changed generation, permission transition, unmount, page error, or
  cancellation discards the candidate scan **as a unit**, leaving the
  previous complete scan in force. On Android/OEM paths without a reliable
  generation token, use an invalidating content observer or decline
  negative reconciliation — never infer a stable snapshot.
- **Coverage is persisted (P4#3):** scans record `coverage = full |
  limited`; generic exact-N / oldest-day claims require `full` coverage,
  and limited-coverage results are labeled as counts of *accessible*
  photos. Tests pin: mutations between pages, primary/SD mount changes,
  all → limited permission transitions, and a stable control scan — an
  unstable scan performs no negative reconciliation and is never promoted.
- **Honest-lazy UI**: with no complete scan (or one still in flight), the
  older-days row shows only the generic "Older days still need review" —
  exact N and oldest-day claims unlock only from the latest complete scan
  (N#4).
- The list: the **3 most recent non-empty photo days** **(autonomous:
  "recent" = non-empty)**, then up to the **2 most recent incomplete older
  days** (visually tagged), then the older-days row, which jumps into
  Progress at the oldest unreviewed day **(autonomous: jump target)**.
  Section title stays "Recent days" **(autonomous)**.
- Large-library test pinning the request/page count of a full index refresh.

### J. Day-progress counts — formulas pinned first  *(#7; R#11)*

Definitions used by every surfaced count (audited against seeded stores;
unit tests pin each number to fixtures including untracked media, restored
media, queued **and** failed intents, active-session kept rows, abandoned
culls, and source-folder filtering):

- **present** = live MediaStore asset after item-G reconciliation. Trashed
  and outside-deleted photos leave both `reviewed` and `total`.
- **total** (day/scope) = present photos in scope (staged culls are still
  present, so still counted).
- **reviewed** = present ∧ state ∈ {kept, done, to-edit-queued, staged
  cull}. Kept and Done merge into "reviewed" (#7) — a keeper awaiting its
  edit is already visible through the to-edit count.
- **culled** = staged culls only (trashed photos have left `total`); a
  staged cull is reviewed / pending confirmation, never remaining work
  (P4#1), and the durable global cull queue survives session replacement
  (item H).
- **to-edit** = present photos with a queued edit.
- **favourited** = present photos with favourite intent `queued` **or**
  `applied` (the chip shows intent, not just outcome) **(autonomous)**.
- **day incomplete** = has ≥ 1 present unreviewed photo. Staged culls and
  pending to-edit work do *not* make a day incomplete.
- **groups per day** (with item C's cross-day groups): group counts and
  completion use **present members only** (N#7). A day's `total groups`
  counts durable groups with ≥ 1 present member taken that day and ≥ 2
  present members overall; a group is `completed` only when **every**
  present member — including out-of-day members — is reviewed. A rendered
  group with fewer than 2 present members dissolves into singles
  (consistent with the ≥ 2 invariant); the durable relation keeps the
  historical rows as provenance **(autonomous)**. An externally deleted
  unreviewed member can never hold a group incomplete, and a day with zero
  present photos reports no groups.
- These counts **overlap**; the UI shows one reviewed/total progress bar
  plus separate stat chips — never a single segmented bar treating them as
  mutually exclusive (R#11).

### K. Source resolution fails closed  *(C#8)*

Several current paths convert `resolveSources()` failure to `null`, whose
documented meaning is **All folders** — DayProgress's "Review this day"
loader, `ProgressView`, and Home's recent-day counts can all silently widen
a transient catalog/permission failure into reviewing or counting photos
outside the user's selected roots, and the new cached day index would make
that mistake durable. Fix: source-resolution failure **retains the last
valid resolved selection or blocks the operation with a retryable error**;
an error is never reinterpreted as an explicit All-folders choice. Injected
catalog-failure tests cover Home, DayProgress replacement, Progress, and
the day-index builder.

### L. Edit detection must not lie  *(C#9)*

`detect.ts` currently marks a queued photo done when its modification time
changed and the content hash is *unavailable* — but an unreadable file is
not evidence its pixels changed — and photos without a baseline hash
complete from metadata alone (only five queued photos receive a baseline
per detection run). This gets more dangerous in m0.7 because organize
deliberately moves files and refreshes URIs. For 0.7.0:

- `hash unavailable` keeps the photo queued/unknown — never `done`;
- verified organize moves refresh the edit-detection URI, modification
  baseline, and hash caches inside item E's post-move repair;
- no auto-completion from a metadata timestamp alone when Afterglow knows
  it just performed that metadata operation itself (organize move,
  favourite flag); and
- orchestration tests: unreadable content, organize while `to_edit`,
  favourite metadata changes, same hash with newer metadata, and a real
  hash mismatch; and
- **"Decide later" is durable (C#12):** detection inserts a detected copy

  resume, and select one best copy per original (multiple matches today
  produce multiple prompts, and culling the original on the first can
  leave later prompts operating on a missing asset).

**Gate 0 (editor-launch diagnostic matrix):**

1. **Matrix entry points** — the failure alert gains a "Run permission
   matrix" button, and long-pressing an Edit-queue row's Edit button opens
   the matrix directly (the proactive path for the emulator and for
   Samsung, where the failure alert may not appear if the fallback viewer
   opens).
2. **Probe semantics** — a dispatch probe resolves the moment Android
   accepts/rejects the intent; whether an app actually opened is recorded
   by the tester per step ("An app opened" / "Nothing opened"), since
   dispatch success does not prove the target drew a screen.
3. **Write-request branch condition** — the `createWriteRequest` step runs
   when **any** probe threw a `SecurityException`, not only the
   write-mode probe: the captured Samsung failure shows read-only VIEW
   failing identically, so a write-only trigger could skip the branch on
   the exact device that needs it.
4. **URI provenance is part of the evidence** —
   `getEditableContentUriDetailed()` records whether the URI came from
   Expo resolution or the synthetic `content://media/external/…` fallback;
   the fallback's shape matches the URI in the captured Samsung failure,
   so the matrix report states which path produced it.
5. **Report delivery** — selectable monospace text plus the system Share
   sheet (no new clipboard dependency); the tester can send the report
   verbatim instead of screenshotting dialogs.
6. **Matrix executed via device automation** — with wireless debugging set
   up on the Samsung tester device, the matrix was driven by UI automation
   (screenshots + UI-dump-targeted taps) rather than handed to a manual
   tester; the emulator ran the identical sequence. Results recorded in
   item A's "Gate 0 result".
7. **Write-request-first Edit launch selected** — per the matrix outcome
   (item A): `createWriteRequest` → EDIT read+write, denial falls back to
   EDIT read-only, VIEW stays read-only.
8. **Gate 3 device verification (2026-07-23, via automation):** the
   two-button edit launch is verified end-to-end on the Samsung tester
   device and the API-36 emulator. Gallery button → Samsung Gallery opens
   read-only; Edit button → `createWriteRequest` consent → editor opens
   with read+write; both round-trips land on the "Done editing?" prompt.
   The fresh-baseline destructive reset was also proven on the Samsung's
