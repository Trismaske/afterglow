# Plan — mobile m0.6 (drafted 2026-07-18)

Response to [Feedback_20260718.md](Feedback_20260718.md) (second tester
round, against desktop v0.5 / mobile m0.5). Desktop needs **no work this
round** — the screensaver passed its first live test (idle timeout fires;
longer-term soak underway), so v0.6 stays the RAW pipeline. Everything
below is **mobile m0.6**. Files referenced are under `apps/mobile/src/`
unless noted.

**Scope decision (Tristan, 2026-07-18):** m0.6 is the mobile
**feature-completion release** — everything previously slotted for m0.7
rides here (stats/streak depth, startup/analysis perf), **except iOS
evaluation, which is deferred post-1.0 until further notice** (no iOS
users or testers today). After m0.6 the mobile train is feature-complete;
what remains to 1.0 is hardening and tester-driven fixes.

**Housekeeping from "Other feedback":** code signing and the standing policy calls
are deferred to the pre-1.0 review (recorded in ASSUMPTIONS.md).

**Repository-review decisions (Tristan, 2026-07-18):** GitHub Releases is
the only release destination; GitLab is deferred until further notice. m0.6
keeps one public version/tag and is delivered through six internal green
gates rather than tester-visible interim versions. Review verdicts have one
rule everywhere: tapping the active Keep, To edit, or Cull state clears the
photo to the default `unreviewed` state. We deliberately do not retain hidden
"previous verdict" history; the default is deterministic across restarts.
Best (★) and favourite (♥) are orthogonal metadata/toggles, not review
verdicts. Applying To edit or Favourite to an unreviewed photo must atomically
make it kept.

## m0.6 — "Feedback: polish the loop"

### 0. Completed groups advance immediately *(late tester feedback)*
The automatic Reconsider pass introduced in m0.5 repeats the group review
with fewer actions and breaks the fast review rhythm. Remove that screen from
the app flow. When a group becomes complete by any path — Keep rest, culling
the last member, moving the last member to Singles, or completing it through
Compare — advance directly to the next unfinished group. If groups were
reviewed out of order, continue forward and then wrap to any earlier unfinished
group before moving to Singles and the cull list. Deliberately opening a group
that was already complete still enters browse/re-decide mode.

### 1. Editor launch — still broken (top priority)  *(feedback #1)*
Neither `ACTION_EDIT` nor the m0.5 `ACTION_VIEW` fallback opens anything on
the Samsung test device. The chain logic (`lib/editFallback.ts`) is sound,
so the next step is evidence-first. Direct intent launch does not need an
Android 11 `<queries>` entry, and Expo does not pre-query handlers here.
- Set explicit `type: 'image/*'` on both intents and reject non-`content://`
  URIs before dispatch — implemented in `lib/edit.ts`.
- Preserve both caught exception messages and show the URI, actions, MIME and
  grants in the failure diagnostic — implemented; do not log private file
  paths automatically.
- Verify EDIT and the simpler VIEW path on Samsung. If Expo still fails, add a
  small native chooser with the same URI/read-write grants. Add `<queries>`
  only if that future code actually queries installed handlers.
- Samsung remains the acceptance gate; code alone cannot prove OEM resolver
  behavior.

### 2. Recent-days progress bar bug — root cause found  *(feedback #11)*
`components/StateProgressBar.tsx` renders segments as `flexGrow: count`
children with **no filler for the unreviewed remainder**, so any nonzero
counts stretch to fill the whole track — 1/14 done renders fully green.
The `total` prop never scales anything. Fix in the component (one place,
both callers): append a transparent filler segment of
`total − sum(counts)`. Home's recent days and the Progress/DayProgress
bars (whose "unreviewed = the empty track" comment never actually held)
are both corrected by it.

### 3. Group cards open the group again  *(feedback #5, #6-last-sentence)*
Tapping a strip thumbnail on the Groups screen stops opening the re-decide
sheet; the whole card — photos included — opens the group (restores the
pre-m0.5 behavior). Re-deciding lives inside the group: the deck's browse
mode (m0.5) already shows verdict chips per photo, and the cull list keeps
its tap-to-change. `screens/GroupsScreen.tsx`.

### 4. Decision indicators everywhere  *(feedback #6, #7)*
One icon per decided photo, same glyphs in both Groups strips and the deck:
- **Cull** — the existing red-circle ✕ (reuse the exact asset both places).
- **Keep** — green tick badge (new).
- **To-edit** — pencil badge (new); edit implies kept (already true in the
  store's CASE remap) and **edit takes display precedence** over keep.
- Deck footer states every verdict, not just culls: "✕ staged to cull"
  (with the same red-circle glyph), "✓ kept", "✎ to edit".

### 5. Decisions can be toggled off  *(feedback #7)*
Re-tapping any active review verdict clears it to the same default:
- active Keep → `unreviewed`;
- active To edit → clear `needs_edit` and return to `unreviewed`;
- active staged Cull → `unreviewed`.

Grouped photos re-enter their deck in original order and reopen the group;
singles re-enter their pending queue. The core `clearDecision` transition,
SessionContext orchestration, re-decide sheet and core regression tests are
implemented. Switching to a different verdict is still direct. There is no
hidden previous-state stack to serialize or recover.

### 6. Unify Singles with the group deck  *(feedback #8, #9 — yes, it makes sense)*
Treat the singles bucket as **one pseudo-group rendered by the same deck
component**: thumbnail strip, free scrolling without being forced to
decide, pinch-zoom, the same decision buttons/indicators, Compare
available against any other single (answers "is there a similar photo
that didn't group?"). `screens/SinglesScreen.tsx` collapses into a
`DeckScreen` mode; core already models singles as a queue — the app feeds
them as a synthetic group ("Keep rest" maps to keeping the remaining
singles). Fewer components, one layout to learn — exactly the tester's
LoC/familiarity point.

### 7. Best button: keep, make it visible — and give it somewhere to go  *(feedback #4)*
It does do things today — stars the best-of-group (fed by Compare's
"X is better") and preserves that relative ranking in compare history — but
nothing shows outside the deck. m0.6: badge the starred photo (★) in the Groups
strip and browse mode alongside the new decision icons, and explain it in the
group summary. Two further consumers make it pay rent:
- **Group cover:** the starred photo becomes the group card's cover
  thumbnail on the Groups screen (falls back to first photo).
- **Favourites hand-off (#11):** starring surfaces a low-friction "♥
  favourite this too?" affordance — but never auto-favourites (best is
  *relative to the group*; favourite is an *absolute* quality call).

### 8. All-time hint only when it applies  *(feedback #2)*
The "All time unlocks after Last year is clear" hint renders only while
the All-time chip is actually visible-and-locked; if All-time or Last year
is disabled in the scope manager, no hint. `screens/HomeScreen.tsx`.

### 9. Pinch-zoom smoothness  *(feedback #3)*
The m0.5 seam (pager pan wins until the pinch activates) is confirmed on
device — works, but hands over late. Attempt: register the pinch
simultaneously with the pager's native scroll gesture
(`simultaneousWithExternalGesture` on the FlatList) and drop the pinch's
activation threshold so two-pointer contact freezes the pager immediately.
Goal: parity with the Compare screen's feel. Timeboxed — if RNGH-vs-pager
arbitration fights back, ship the improvement we get and note the rest.

### 10. Similarity — no scale change  *(feedback #10)*
The new scale is field-verified (lighting-difference groups form; 64 =
time-only grouping is the intended extreme). Loosest-as-preference is what
the chips + slider are for; once singles share the group layout (#6), the
strictness stakes drop further. Only change: the slider explainer gains
what the number means — "how many of the 64 fingerprint bits may differ;
64 = grouping by time alone".

### 11. Favourites queue  *(new — Tristan's direction, 2026-07-18)*
A **♥ favourite** decision, deliberately separate from ★ best: best is
"the winner of this group", favourite is "good, full stop". Not every
group's best deserves a favourite; a great group can produce several.
- Heart from the deck, browse mode, and Compare (any photo, grouped or
  single; independent of keep/edit state — a favourite is implicitly
  kept).
- Favourites accumulate in a **favourites queue** (sibling of the to-edit
  queue) and are **applied to the system gallery's own mechanism**:
  Android 11+ `MediaStore.createFavoriteRequest` — one batched system
  confirm dialog, exactly the shape of our delete flow. Samsung Gallery /
  Google Photos both surface `IS_FAVORITE` as their heart.
- Needs a small local native module (precedent exists:
  `apps/mobile/modules/material-you-accent`). SDK 57's new Asset API exposes
  one-asset `setFavorite`, but not the required one-confirm batch, so the
  native boundary remains justified. Runtime-guard on API 30+; hide the
  feature below.
- SQLite state is `none / queued_apply / applied / queued_remove / error`,
  with timestamps. Applying/removing is idempotent, resumable, and verified
  against `IS_FAVORITE` before the queue commits. Tapping an applied heart
  queues an explicit unfavourite; it does not silently leave gallery state.
- The shared MediaStore-actions module and durable queue/store foundation are
  implemented. Samsung Gallery display remains a device acceptance gate and
  must not be promised until observed.

### 12. Stats & streak depth  *(pulled forward from m0.7)*
Lifetime numbers, somewhere between Summary and Progress: photos
reviewed / culled / storage reclaimed all-time, edits completed,
favourites applied, current + longest streak. Modest scope — a stats
card, not a dashboard. Metrics count unique photos that have ever reached
their first durable event; reclaimed bytes count successful trash batches.
The v6 migration now records `reviewed_at`, `culled_at`,
`edit_completed_at`, `favourite_applied_at`; current/longest streak math is a
tested pure helper. The card remains part of gate 4.

### 13. Startup & analysis perf  *(pulled forward from m0.7)*
Profile first, then fix the top offenders. Known candidates: Home's
per-recent-day MediaStore count queries on focus (the logged known
limit — consolidate into one ranged query), dHash analysis batching/yield
so big sessions don't jank (hash cache `photo_hashes` already avoids
recompute), cold-start bundle/first-render pass.

### 14. Design pass: icons  *(tester feedback via Tristan)*
- The **dark app icon** is already wired in `app.json` (landed after the
  m0.5 tag) — it ships with the m0.6 APK automatically.
- The ⚙️ emoji gear on Home "looks out of place" — replace with a
  **Material icon** (`@expo/vector-icons`, `npx expo install`; ships with
  the Expo dev client, no config plugin). While at it, render the new
  decision indicators (#4) and ♥/★ with Material glyphs too, not
  unicode/emoji — one icon language across the app. Audit remaining
  emoji/unicode glyphs in headers and buttons.

*Done when: completing a group immediately opens the next unfinished group;
the Samsung tester taps Edit and lands in an editor (or the gallery); a 1/14
day renders a 7% bar; tapping anywhere on a group card opens it; every decided
photo shows cull / keep / edit / best marks in
strip and deck (Material glyphs, not emoji); a re-tap clears a decision;
singles scroll freely in the deck layout with a strip; the All-time hint
is gone when the scope is disabled; hearting photos favourites them in
the system gallery after one confirm; a stats card shows lifetime
totals + streaks; Home focus does one count query, not one per day.*

## Internal delivery gates — one public m0.6

There is one tester-facing `mobile-m0.6` tag. Every gate returns the full
repository to green before the next begins; gate names are internal only.

1. **Data safety and foundations — green:** Android 11+ recoverable
   `createTrashRequest` with no permanent fallback; cancellation/error split;
   FIFO persistence retry barrier; atomic schema runner and fresh/v5/failure
   tests; hardened snapshots.
2. **Feedback and decision model:** items 0–5, 8, 10 and the icon pass, with
   focused tests. Samsung editor verification can remain pending until gate 6.
3. **Deck/singles unification:** item 6 plus group navigation, compare and
   touched-screen maintainability/orchestration coverage.
4. **Favourites and stats:** item 7 consumers, item 11 UI/batch retry, item 12
   card and totals tests. Favourite activation implies keep; clearing the
   heart queues unfavourite.
5. **Measured performance and gestures:** profile before/after item 13 and
   timebox item 9; no speculative rewrite.
6. **Release candidate:** lint, format, typecheck, all unit tests, Metro
   export, clean Expo prebuild, Gradle debug/release builds, emulator flows,
   Samsung checklist (editor, trash+restore, favourite visibility,
   pinch/pager, upgrade-in-place), release preflight, expected-artifact and
   checksum proof. Only then create the GitHub Release. GitLab does not
   participate until explicitly revived.
